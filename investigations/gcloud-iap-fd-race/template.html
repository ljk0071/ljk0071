gcloud IAP fd 경합 추적기

    장애 분석 · 2026-09-17 ~ 2026-09-26

    gcloud IAP tunnel은 왜 자기 설정 DB에 TLS 메시지를 써 넣었나

    운영 중인 Spring Boot 앱이 간헐적으로 PostgreSQL에 연결하지 못했다. 원인은 DB도 네트워크도 아니었다. DB 앞단의 gcloud compute start-iap-tunnel이 이미 닫은 파일 디스크립터(fd) 번호로 계속 읽고 쓰다가, 그 번호를 새로 받은 자신의 SQLite 설정 파일에 TLS alert 24 bytes를 써 넣고 있었다. 이 페이지는 증상에서 syscall 한 줄까지 범위를 좁혀 간 과정과 그 증거를 담았다.

    Google Cloud SDK 582.0.0 bundled Python 3.14.7 bundled OpenSSL 3.5.7 (정적 링크) Linux 6.12 (Oracle Linux 9 UEK) ✔ syscall 수준 확증

    한눈에 보기

    증상

    Spring이 ConnectionFactoryImpl.enableSSL()에서 Read timed out. 이후 새 DB 연결이 전부 실패. 그런데 gcloud process와 :15432 listener는 살아 있었다.

    근본 원인

    gcloud IAP tunnel의 fd use-after-close race. 연결 종료 thread가 SSL socket을 닫는 동안 수신 thread는 OpenSSL 안에서 같은 원시 fd 번호로 계속 읽고 쓴다.

    트리거

    클라이언트(Hikari pool)가 연결을 닫고 곧바로 새 연결을 연다. 새 연결이 default_configs.db를 열 때 방금 반납된 fd 번호를 받는다.

    영향

    default_configs.db offset 29에 17 03 03 00 13 + 19 bytes가 들어가 손상. 이후 모든 새 tunnel 연결과 같은 설정을 쓰는 모든 gcloud 명령이 database disk image is malformed로 실패.

    배제된 것

    PostgreSQL 서버, GCP VM, IAP 서비스, 네트워크 경로, system OpenSSL 혼용, proxy/LD 환경변수. gcloud 583~586 릴리스 노트에 관련 수정 없음.

    아직 추정인 것 1건

    같은 race가 DB 파일이 아니라 다른 연결의 socket에 걸리는 변형. 초기의 간헐적 Read timed out을 설명할 수 있지만 syscall로 잡지는 못했다.

    결정적 한 줄 · 2026-09-26 19:31:20, 수신 thread 1421083이 fd 7로 read(29)를 해서 SQLite 헤더를 읽은 뒤, 같은 fd 7로 write(24)를 했다. 그 24 bytes(17 03 03 00 13 aa 23 cb …)가 손상된 DB의 offset 29 내용과 byte 단위로 일치한다. fd 7은 140ms 전에 다른 thread가 닫은 WebSocket socket 번호였다. → 확증 타임라인
    English summary. A long-running gcloud compute start-iap-tunnel (SDK 582.0.0, lightweight WebSocket path) intermittently broke all new tunnel connections while the process and its listener stayed up. We traced it to an fd use-after-close race: the per-connection handler thread closes the WebSocket's SSL socket without synchronizing with the receive thread, which is still inside OpenSSL's SSL_read holding the raw integer fd from SSL_set_fd. When a new connection opens default_configs.db and receives the same fd number, the stale reader reads 29 bytes of the SQLite header, fails to decrypt them, and writes a 24-byte TLS 1.3 alert record (17 03 03 00 13…) into the database at offset 29. bpftrace captured the full close(7) → openat(db)=7 → read(7,29) → write(7,24) chain in production, and the written bytes match the corrupted file exactly.

    조사 여정: 범위를 좁혀 간 16단계

    각 단계는 가설 → 한 일 → 관측 → 결론 순서로 적었다. 오른쪽 막대는 그 시점에 "gcloud 내부 fd race"라는 최종 결론에 대해 가졌던 확신 정도다.

      확증: 2026-09-26 19:31:20의 syscall 타임라인

      production gcloud process에 붙여 둔 bpftrace가 기록한 이벤트 중, 관련된 thread 3개와 fd 7만 추렸다. 기준점 t0는 연결 [93]의 처리 thread가 WebSocket socket(fd 7)을 close()한 순간이다. 위쪽 띠는 그 시점에 fd 7 번호가 무엇을 가리켰는지를 보여 준다.

      fd 7 = WebSocket SSL socket fd 7 = 다른 설정 파일(active_config) fd 7 = default_configs.db ● read · ■ write · ✕ close · ▲ open · ◆ 손상

      무엇이 일어났나

      1. 1421083(연결 [93]의 수신 thread)은 95초 전부터 fd 7에서 다음 TLS record를 기다리며 read() 안에 잠들어 있었다.
      2. 1421118(연결 [93]의 처리 thread)이 local EOF를 받고 WebSocket Close를 보낸 뒤 fd 7을 닫았다.
      3. 4.9ms 뒤 1431669(새 연결 [94])가 설정 파일들을 열었고, 커널은 가장 낮은 빈 번호인 7을 줬다.
      4. 140ms 뒤 서버 frame이 도착해 1421083이 깨어났다. 잠들어 있던 read()는 옛 socket에서 record header를 받았고, OpenSSL은 본문 29 bytes를 더 읽으려고 read(7, 29)를 다시 불렀다. 이때 7은 이미 DB 파일이었다.
      5. SQLite 헤더를 복호화할 수 없으니 OpenSSL은 fatal alert를 보냈다. write(7, 24)가 파일 위치 29, 즉 방금 29 bytes를 읽은 바로 그 자리에 떨어졌다.

      왜 이것이 확증인가

      • DB에 쓴 주체와 syscall, 파일 위치, bytes가 모두 기록에 있다. 이제 "구조가 닮았다"는 추론이 아니다.
      • trace의 write payload와 손상 파일의 offset 29 bytes가 일치한다. Hex 뷰어에서 나란히 비교할 수 있다.
      • offset 29라는 이상한 위치가 직전 read 29 bytes로 정확히 설명된다. 4번의 손상이 모두 offset 29였다.
      • 쓴 thread의 이름은 Thread-275 (_ReceiveFromWebSocket)이고, user stack은 __write ← 정적 OpenSSL ← _ssl ← Python이다.

      Hex 뷰어: 손상된 default_configs.db

      관측한 손상 파일 4개의 앞 96 bytes다. 노란 칸이 덮어써진 24 bytes(offset 29~52)이고, 빨간 테두리는 TLS record header 5 bytes다. 칸에 마우스를 올리거나 탭하면 그 위치의 SQLite 헤더 필드가 나온다.

      칸을 가리키면 SQLite 헤더 필드 설명이 표시됩니다.

      덮어쓴 24 bytes의 구조 (TLS 1.3 record)

      trace에 기록된 write payload (19:31:20)

      손상 파일 offset 29~44 (같은 날짜 파일)

      19 = 2 + 1 + 16. TLS 1.3에서는 alert도 암호화된 application-data record(type 0x17)로 나간다. 본문은 alert 2 bytes, 실제 content type 1 byte, AEAD 인증 태그 16 bytes를 합쳐 19 bytes(0x13)다. 연결마다 키가 다르므로 header 5 bytes는 매번 같고 뒤 19 bytes는 매번 다르다. 4개 파일이 정확히 그랬다.
      DB가 "malformed"가 된 이유. offset 28~31은 SQLite의 database size in pages다. 원래 00 00 00 03(3 pages)이어야 할 값이 00 17 03 03, 즉 1,508,099 pages가 됐다. 이어서 freelist 정보, schema cookie, schema format(offset 32~52)까지 덮였다.

      코드 경로: 동기화 없는 두 thread

      gcloud는 tunnel로 들어오는 TCP 연결 하나마다 thread 두 개를 쓴다. 둘은 같은 SSL socket을 공유하지만, 닫는 쪽은 읽는 쪽이 끝나기를 기다리지 않는다.

      닫는 쪽 · RunReceiveLocalData thread
      1. conn.recv()가 빈 값 → local EOF
      2. finally: conn.close() (trace: shutdown(6), close(6))
      3. IapTunnelWebSocket.Close() → helper.SendClose() (write(7))
      4. helper.Close() → IapLightWeightWebsocket.close()
      5. if self.connected and self.sock: → self.sock.close()
        fd 7 반납. 수신 thread를 join하지 않고 lock도 없다
      읽는 쪽 · _ReceiveFromWebSocket thread
      1. run_forever() 루프: while self.connected:
      2. self.recv() → recv_frame() → _recv_bytes()
      3. self.sock.recv_into() (Python SSLSocket)
      4. _ssl C 모듈 → OpenSSL SSL_read()
        GIL을 놓고 실행. fd는 SSL_set_fd 때 받은 정수 7
      5. OpenSSL 내부에서 read(7) / 실패 시 alert write(7)
        Python의 fd=-1 보호를 거치지 않는다

      왜 Python의 보호가 통하지 않았나

      Python socket 객체는 close()하면 자기 fd를 -1로 바꾼다. 그래서 Python 코드가 닫힌 socket을 다시 써도 fd=-1로 syscall이 나가 EBADF로 안전하게 실패한다. 문제는 TLS 읽기와 쓰기를 실제로 하는 OpenSSL이 이 값을 보지 않는다는 점이다.

      OpenSSL 원시 fdread실제 번호 (7, 8, 11, 12, 17, 23)6위험 번호가 재사용됐으면 남의 파일이나 socket을 읽음

      원시 fd read()가 close 뒤 얼마 만에 일어났나

      실험실 6건은 close 후 0.07~110.68ms 사이였다. production near-miss는 89.46ms, 확증 사건은 139.97ms였다. 이 사이에 다른 thread가 파일을 열면 번호가 겹친다.

      수정 제안 (gcloud 쪽)

      1. 닫는 순서를 바꾼다

      sock.shutdown(SHUT_RDWR)로 수신 thread의 read를 깨우고, 그 thread를 join()한 뒤에만 close()한다. 아니면 socket 소유권을 수신 thread에 주고 닫기도 그쪽에서 하게 한다.

      2. close와 I/O를 같은 lock으로

      IapLightWeightWebsocket.close()는 lock 없는 check-then-act다. send에서 쓰는 lock을 close와 수신 경로에도 적용하고, close가 시작되면 run_forever가 더 읽지 않게 한다.

      의사 코드
      def close(self):
    with self._lock:
        if not self.connected:
            return
        self.connected = False            # run_forever 루프가 더 읽지 않게
        try:
            self.send_close()
        finally:
            self.sock.shutdown(socket.SHUT_RDWR)   # 블로킹 read 를 깨움 (fd 는 아직 살아 있음)
    if threading.current_thread() is not self._receiver:
        self._receiver.join(timeout=5)     # 수신 thread 가 OpenSSL 밖으로 나온 뒤
    self.sock.close()                      # 그때 비로소 번호 반납

      운영 교훈

      listener가 살아 있어도 end-to-end가 정상인 것은 아니다

      TCP connect 성공은 tunnel이 건강하다는 뜻이 아니다. PostgreSQL SSLRequest(00 00 00 08 04 d2 16 2f)를 보내 'S'/'N'를 받는 probe가 필요하다. A/B 시험에서 :15432는 connect 0.1ms에 성공하고 SSLRequest에서 reset됐다.

      독립 경로 대조군이 가장 빨리 범위를 줄인다

      같은 목적지로 가는 다른 호스트의 tunnel이 같은 시각에 'S'를 받았다. 이 한 번의 비교로 원격 전체(PG, VM, IAP, 네트워크)가 빠졌다.

      감시 도구도 검증해야 한다

      eBPF 필터가 s_dev == 0xfc00(사용자 공간 표기)였다. 커널 값은 0xfc00000(MKDEV)라 필터가 한 번도 참이 되지 않았다. "기록 없음"을 "사건 없음"으로 믿었다가 철회했다. 필터는 알려진 이벤트로 먼저 시험해야 한다.

      1차 원인과 2차 증폭을 분리한다

      앱 전체가 멈춘 직접 원인은 Slack 알림 코드였다. timeout 없는 동기 호출, .body(sendSlack(...)) 이중 호출, 컨테이너에 없던 webhook URL(기본값이 자기 자신)이 겹쳐 self-deadlock이 났다. 고치지 않았다면 DB 원인을 찾아도 장애 규모는 그대로였을 것이다.

      숫자의 모양이 가설을 준다

      24 bytes, 0x13 = 19 = 2 + 1 + 16, 그리고 항상 offset 29. 이 크기와 위치가 "암호화된 TLS alert가 파일에 쓰였다", 이어서 "fd 번호가 섞였다"는 가설을 곧바로 가리켰다.

      재현이 안 되면 관측을 옮긴다

      실험실 약 10,000연결로도 손상은 재현되지 않았다. 대신 운영 process에 PID를 따라가는 tracer와 손상 즉시 증거를 보존하는 supervisor를 붙였고, 다음 자연 발생에서 전체 syscall 사슬을 얻었다.

      용어집

      fd (file descriptor)
      process가 연 파일이나 socket을 가리키는 작은 정수. Linux는 새로 열 때 비어 있는 가장 작은 번호를 준다.
      use-after-close
      이미 close()한 fd 번호를 계속 쓰는 버그. 번호가 재사용되면 전혀 다른 파일이나 socket에 읽고 쓰게 된다.
      race (경합)
      두 thread의 실행 순서에 따라 결과가 달라지는 상태. 여기서는 "닫기"와 "읽기"의 순서.
      TLS record
      TLS가 데이터를 나르는 단위. header 5 bytes(type 1, version 2, length 2) 뒤에 본문이 온다. TLS 1.3에서는 alert도 0x17로 암호화되어 나간다.
      AEAD tag
      암호문에 붙는 16 bytes 인증 태그. 이것이 맞지 않으면 복호화 실패로 연결을 끊고 alert를 보낸다.
      SSL_set_fd
      OpenSSL에 socket의 정수 fd를 넘겨주는 함수. OpenSSL은 이후 이 번호로 직접 read()/write()를 한다.
      EBADF
      "잘못된 fd" 오류. 닫힌 번호를 쓰면 나지만, 번호가 이미 재사용됐다면 나지 않고 남의 대상에 조용히 쓴다.
      bpftrace
      커널 eBPF로 syscall과 커널 함수를 추적하는 도구. 여기서는 gcloud PID 하나만 골라 fd 수명과 I/O를 기록했다.
      SSLRequest
      PostgreSQL 클라이언트가 TLS를 쓰겠다고 알리는 8 bytes 요청. 서버는 1 byte('S' 또는 'N')로 답한다.
      IAP TCP forwarding
      Google Cloud의 Identity-Aware Proxy가 외부 IP 없는 VM으로 TCP를 중계하는 기능. 클라이언트 쪽은 gcloud compute start-iap-tunnel이 WebSocket over TLS로 연결한다.
