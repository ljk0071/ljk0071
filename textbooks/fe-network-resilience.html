00 · 시작하기

따라 하며 이해하는 불안정한 네트워크와 프론트엔드

BE 개발자가 API를 설계할 때 FE가 네트워크 문제를 어떻게 다루는지 이해하기 위한 실습 문서입니다. 각 장의 실습에서는 실제 TanStack Query v5 코어(@tanstack/query-core)가 브라우저에서 동작하고, 네트워크(지연·유실·끊김·오프라인·망 전환)와 서버(Spring 쪽 동작)는 시뮬레이션합니다. Chrome DevTools로는 재현하기 어려운 "서버는 처리했는데 응답만 사라진" 상황도 버튼 하나로 만들 수 있습니다.

실습 화면 읽는 법

따라하기

번호 단계를 순서대로 진행합니다. 할 일에 나오는 버튼 이름 칩에 마우스를 올리면 실습 안의 그 버튼이 강조되고, 누르면 그 위치로 이동합니다. 이 단계 설정으로 맞추기를 누르면 필요한 선택·토글이 자동으로 맞춰지고, 실행 버튼은 직접 누릅니다. "예상해 보기"로 결과를 먼저 짐작해 보세요.

개선 전 / 개선 후

흔한 구현과 권장 구현(FE 설정 + BE 계약)을 한 번에 전환합니다. 개별 토글로 한쪽만 바꿔 볼 수도 있습니다.

장애 주입 버튼

점선 테두리 버튼(예: 다음 응답 유실)은 다음 요청 한 번에만 장애를 겁니다. 켜 두면 "대기 중"으로 표시됩니다.

코드 탭

FE(React + TanStack Query), BE(Kotlin + Spring Boot 4), HTTP 메시지를 보여 줍니다. 방식·토글을 바꾸면 코드도 지금 설정 그대로 바뀌고, 달라진 줄은 잠깐 파랗게 강조됩니다(다른 탭이 바뀌면 탭 이름 옆에 점). + 줄은 개선으로 추가된 부분, ! 줄은 문제 지점입니다.

추천 순서

1장부터 차례로 읽어도 되지만, 실습만 따라가려면 아래 순서가 자연스럽습니다. 한 번이라도 단계를 진행한 실습에는 ✓가 붙습니다(이 브라우저에만 저장).

이 문서의 전제

예제 도메인은 가상의 쇼핑몰(products · orders · payments · cart · uploads)입니다. 시뮬레이터의 시간·지연 값은 관찰하기 쉽게 고른 것이고 실측값이 아닙니다. 라이브러리 동작(재시도·중복 제거·취소·일시정지·scope 직렬화)은 실제 @tanstack/query-core가 수행하므로 문서와 같게 움직입니다.

01 · 문제 정의

정규화 캐시 vs 문서 캐시

Apollo는 객체를 __typename:id로 평탄화해 저장하므로, 같은 상품을 다섯 개 화면이 참조해도 실체는 하나이고 하나를 고치면 모두 갱신됩니다. TanStack Query·SWR·RTK Query는 키 단위 문서 캐시라서 "이 수정이 끝나면 이 키들을 무효화"를 명시합니다(RTK Query는 태그로 선언). 정규화는 편하지만 필드 정책이 복잡해질 수 있고, 문서 캐시는 단순하지만 무효화 대상을 개발자가 알아야 합니다. BE 관점에서는 두 경우 모두 안정적인 id와 수정 후 무엇이 바뀌는지 예측 가능한 응답이 도움이 됩니다.

03 · Mutation · 재시도

재시도와 멱등성 — 무엇을, 언제, 몇 번

세 개의 실습으로 진행합니다. ① 조회(GET)의 재시도와 백오프, ② 많은 클라이언트가 동시에 재시도할 때 서버에 생기는 일, ③ 결제(POST) 재시도가 이중 결제가 되는 과정과 Idempotency-Key로 막는 방법.

정리

재시도해 볼 가치가 있는 오류
  • 네트워크 오류(연결 실패·리셋·오프라인)
  • 타임아웃
  • 429 — Retry-After만큼 기다린 뒤
  • 502 · 503 · 504 (500은 상황에 따라)
재시도해도 결과가 같은 오류
  • 400 · 401 · 403 · 404 · 409 · 422
  • 401은 토큰 갱신 후 1회만 다시 보내는 별도 흐름
  • 409는 멱등 키 "처리 중" 응답일 때만 대기 후 재시도
이중 결제 방지에서할 수 있는 것할 수 없는 것
FE재시도 여부·횟수·간격 결정, 버튼 잠금, "확인 중" 표시, 키 발급과 재사용응답 없이 서버의 처리 여부를 알아내기, 중복 실행 자체를 막기
BE키 선점(PK), 응답 저장·재생, 처리 중 409, 본문 불일치 422, 키 없음 400, 보관 기간FE가 재시도마다 새 키를 만드는 실수 막기(계약 위반)
표준화 현황

Idempotency-Key는 IETF httpapi 워킹그룹의 Internet-Draft(draft-ietf-httpapi-idempotency-key-header-07)로, 2026년 9월 현재 RFC가 아닙니다. 초안은 키로 UUID 같은 무작위 값을 권장하고, 헤더 값을 Structured Field 문자열(따옴표 포함)로 정의합니다. Stripe 등 결제사가 같은 방식을 오래 써 왔습니다(Stripe는 응답에 Idempotent-Replayed 헤더를 붙입니다).

출처: TanStack Query Retries · Mutations (retry 기본 0, scope) · IETF Idempotency-Key draft-07 · Stripe Idempotent requests · Spring Framework 7 Resilience (@Retryable) · RFC 9110 Retry-After

04 · 서버 상태 · 캐시

오프라인 / 온라인

오프라인에서 사용자가 한 행동을 버리지 않고, 앱을 다시 켜도 남겨 두었다가, 온라인이 되면 순서대로 서버에 반영하는 흐름을 실습합니다. 그 과정에서 BE가 지켜야 할 계약(멱등 키, 재검증, 명확한 거절 이유)이 드러납니다.

정리

단순 오프라인 UX

오프라인이면 배너를 띄우고 요청을 멈춥니다(TanStack Query 기본 networkMode: 'online'). 구현 비용이 낮고 대부분의 관리 도구·대시보드에 충분합니다.

오프라인 우선 (offline-first)

로컬 데이터 사용 → 쓰기를 큐에 저장 → 온라인 시 동기화 → 충돌 해결. 노트, 현장 업무 앱, 협업 문서처럼 오프라인에서도 일이 계속돼야 할 때만 정당화되는 복잡도입니다.

  • navigator.onLine과 online/offline 이벤트는 신뢰도가 낮습니다(LAN만 연결돼도 online). 실제 요청 성공·실패로 보완합니다.
  • Background Sync API는 2026년 현재 Chromium 계열만 지원하고 Safari·Firefox는 지원하지 않습니다. 앱이 다시 열리거나 포그라운드로 돌아올 때 동기화하는 방식이 여전히 필요합니다.
  • 영속화 저장소로는 용량 제한이 작고 동기 API인 localStorage보다 IndexedDB가 적합합니다.

출처: TanStack Query Network Mode · Persisting Offline mutations · persistQueryClient · MDN Navigator.onLine · caniuse Background Sync · RFC 9457 Problem Details

05 · 서버 상태 · 캐시

캐시와 stale 데이터

FE에는 캐시가 여러 층 있습니다. 실습에서는 그중 두 층, TanStack Query의 메모리 캐시(staleTime·gcTime)와 브라우저 HTTP 캐시(ETag·Cache-Control)가 요청 하나를 어떻게 나눠 처리하는지 봅니다.

정리: 네 개의 캐시 층

층저장하는 것답하는 질문BE가 주는 것
브라우저 HTTP 캐시HTTP 응답(바이트)네트워크에 갈 필요가 있나? 가면 본문을 다시 받아야 하나?Cache-Control, ETag, Last-Modified
Service Worker Cache요청-응답 쌍(앱이 직접 관리)네트워크가 아예 없을 때 무엇을 줄까?(정적 자원 버전 관리)
TanStack Query 캐시파싱된 객체 + 상태(stale, fetching, error)화면에 무엇을 보여 주고, 언제 다시 물어볼까?안정적인 응답 구조, 변경 후 무효화할 키를 알 수 있는 API
IndexedDB 영속화위 캐시의 스냅샷앱을 다시 켰을 때 무엇을 바로 보여 줄까?—
staleTime vs gcTime

staleTime: 다시 물어볼 필요가 있는가(신선도). gcTime: 화면에서 사라진 캐시를 언제 지울까(보관). stale이어도 캐시 값은 즉시 보여 주고 뒤에서 재검증합니다(stale-while-revalidate, 원래 RFC 5861의 HTTP 개념).

staleTime vs max-age

staleTime은 "JS가 fetch를 다시 부를지", max-age·ETag는 "그 fetch가 서버까지 갈지, 본문을 다시 받을지"를 정합니다. API에는 보통 no-cache + ETag, 신선도 판단은 staleTime에 맡깁니다.

Spring에서

ResponseEntity.ok().eTag(...)로 응답하면 Spring MVC가 GET/HEAD의 If-None-Match를 비교해 자동으로 304를 돌려줍니다. 본문을 만드는 비용 자체를 아끼려면 WebRequest.checkNotModified(etag)로 먼저 확인합니다.

출처: TanStack Query Important Defaults · MDN HTTP Caching · RFC 9111 · RFC 5861 · Spring MVC HTTP Caching

07 · Mutation · 재시도

요청 취소

검색어 자동완성에서 "a → ap → app"이 빠르게 입력되면 응답이 뒤죽박죽 도착합니다. 취소 없이, AbortController로, TanStack Query로 각각 무엇이 보이는지 비교합니다.

정리

  • AbortController + fetch가 표준 취소 방법입니다. Axios의 CancelToken은 deprecated이고 AbortController(signal)를 쓰는 것이 현재 권장입니다.
  • TanStack Query는 queryFn에 signal을 넘기고, 쿼리 키가 바뀌거나 컴포넌트가 언마운트돼 구독자가 사라지면 그 signal을 abort합니다(signal을 fetch에 넘긴 경우).
  • 취소는 브라우저가 응답을 기다리지 않게 할 뿐입니다. 서버 부하를 줄이려면 디바운스(FE)와 최소 검색어 길이·캐시(BE)가 필요합니다.
