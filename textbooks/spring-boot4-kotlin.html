    1장 커스텀 인자 주입 (@LoginUser)

    컨트롤러 파라미터에 로그인 사용자 같은 값을 넣는 방법입니다. 리졸버를 직접 만드는 방법, Spring Security의 방법, 더 가벼운 대안을 차례로 봅니다.

    이 장의 핵심

    • 커스텀 리졸버는 addArgumentResolvers로 등록하며, 내장 리졸버 뒤에 실행됩니다.
    • Principal 하위 타입은 내장 리졸버가 먼저 가져가므로 전용 타입(AuthUser)을 씁니다.
    • 리졸버가 만든 값에는 @Valid가 자동으로 적용되지 않습니다.

    1.1 기본 구성 요소

    • supportsParameter(MethodParameter): 이 리졸버가 처리할 파라미터인지 판단합니다. 보통 어노테이션과 타입을 함께 확인합니다.
    • resolveArgument(MethodParameter, ModelAndViewContainer?, NativeWebRequest, WebDataBinderFactory?): 주입할 값을 만듭니다. 원본 요청은 getNativeRequest(HttpServletRequest::class.java)로 꺼냅니다.
    • WebMvcConfigurer.addArgumentResolvers: 리졸버를 등록합니다. 이렇게 등록한 리졸버는 내장 리졸버 뒤에 붙습니다.
    • MethodParameter.isOptional: 파라미터가 Kotlin nullable 타입이면 true입니다. 값이 필수인지 판단할 때 씁니다.
    @Target(AnnotationTarget.VALUE_PARAMETER)
@Retention(AnnotationRetention.RUNTIME)
annotation class LoginUser(val required: Boolean = true)

@Component
class LoginUserResolver(private val users: UserQuery) : HandlerMethodArgumentResolver {
    override fun supportsParameter(p: MethodParameter) =
        p.hasParameterAnnotation(LoginUser::class.java) && p.parameterType == AuthUser::class.java
    override fun resolveArgument(p: MethodParameter, m: ModelAndViewContainer?,
                                 r: NativeWebRequest, b: WebDataBinderFactory?): Any? {
        val jwt = SecurityContextHolder.getContext().authentication?.principal as? Jwt
        val user = jwt?.let { users.find(it.subject) }
        if (user == null && p.getParameterAnnotation(LoginUser::class.java)!!.required && !p.isOptional)
            throw UnauthenticatedException()
        return user
    }
}
@Configuration
class WebConfig(private val r: LoginUserResolver) : WebMvcConfigurer {
    override fun addArgumentResolvers(resolvers: MutableList<HandlerMethodArgumentResolver>) { resolvers += r }
}

    1.2 우선순위 문제

    파라미터 타입이 Principal의 하위 타입이면 내장 리졸버가 먼저 가져가서 커스텀 리졸버가 호출되지 않습니다. 해결 방법은 세 가지입니다.

    • Principal을 구현하지 않는 전용 타입(AuthUser)을 씁니다.
    • BeanPostProcessor에서 RequestMappingHandlerAdapter.setArgumentResolvers로 커스텀 리졸버를 목록 맨 앞에 넣습니다.
    • WebMvcRegistrations.getRequestMappingHandlerAdapter()로 어댑터를 교체합니다.

    1.3 Spring Security 방식

    • @AuthenticationPrincipal(expression = "claims['sub']"): AuthenticationPrincipalArgumentResolver가 principal을 주입합니다.
    • @CurrentUser: @AuthenticationPrincipal을 메타 어노테이션으로 붙여 만든 커스텀 어노테이션입니다. 6.4부터는 AnnotationTemplateExpressionDefaults로 속성 템플릿을 쓸 수 있습니다.
    • @CurrentSecurityContext(expression = "authentication.name"): SecurityContext에서 표현식으로 값을 꺼내 주입합니다.

    1.4 대안

    • HandlerInterceptor + @RequestAttribute: 인터셉터에서 테넌트 같은 값을 파싱해 요청 속성에 넣고, 핸들러에서 꺼내 씁니다.
    • @ControllerAdvice의 @ModelAttribute: 모든 핸들러에 공통 모델 값을 넣습니다.
    • Converter<String, OrderId> / Formatter: @PathVariable, @RequestParam 값을 커스텀 타입으로 변환합니다.
    • @RequestHeader("Idempotency-Key") key: String?: 헤더 값을 바로 주입합니다.

    1.5 검증·테스트·suspend

    • 검증: 리졸버가 만든 값에는 @Valid가 자동으로 적용되지 않습니다. binderFactory.createBinder(...)로 바인더를 만들어 validate()를 호출하고, 실패하면 MethodArgumentNotValidException을 던지세요.
    • 테스트:
      • standaloneSetup(ctrl).setCustomArgumentResolvers(r)로 리졸버를 직접 등록합니다.
      • @WebMvcTest에서는 @MockitoBean을 씁니다. Boot 4에서 @MockBean이 제거됐습니다.Boot 4
      • 인증 사용자는 @WithMockUser나 SecurityMockMvcRequestPostProcessors.user() / authentication() / jwt { }로 주입합니다.
      • 복잡한 인증 상태는 커스텀 @WithSecurityContext로 만듭니다.
    • suspend 컨트롤러: 리졸버는 코루틴이 시작되기 전에 요청 스레드에서 실행되므로 안전합니다. 다만 코루틴 본문에서 디스패처를 바꾼 뒤에는 SecurityContextHolder가 비어 있을 수 있습니다.

    2장 Bean Validation

    Jakarta Validation 3.1의 내장 제약과 Hibernate Validator 추가 제약을 타입별로 정리하고, Kotlin에서 어노테이션이 엉뚱한 곳에 붙는 함정과 MVC 메서드 검증의 예외 구분을 다룹니다.

    이 장의 핵심

    • @NotNull, @NotEmpty, @NotBlank, @Null을 뺀 모든 제약은 null을 유효한 값으로 봅니다.
    • Kotlin에서는 컴파일 옵션이나 @field:로 어노테이션 적용 대상을 확실히 합니다.
    • 파라미터 제약 실패는 HandlerMethodValidationException, 바디 객체 실패는 MethodArgumentNotValidException입니다.

    2.3 컨테이너·그룹·커스텀 제약

    • 컨테이너 원소 제약: List<@NotBlank String>, Map<@NotNull K, @Positive Int>, Optional<@Min(1) Int>처럼 원소 타입에 직접 붙입니다.
      • 컨테이너 쪽에는 @Valid가 필요 없습니다.
      • 위반 경로는 parts[1].<list element> 형태로 나옵니다.
    • cascade: @Valid를 붙이거나 List<@Valid Person>처럼 씁니다. 직접 만든 컨테이너 타입은 ValueExtractor를 구현해야 합니다.
    • 그룹:
      • groups 속성으로 제약마다 그룹을 지정합니다.
      • @GroupSequence는 앞 그룹이 실패하면 뒤 그룹 검증을 중단합니다.
      • @GroupSequenceProvider(HV)는 시퀀스를 동적으로 정합니다.
      • @ConvertGroup(from, to)는 그룹을 변환합니다.
      • Spring에서는 @Validated(OnCreate::class)로 그룹을 지정합니다.
    • 커스텀 제약:
      • @Constraint(validatedBy = [V::class])를 붙이고 message, groups, payload를 반드시 선언합니다.
      • ConstraintValidator에는 Spring 빈을 주입할 수 있습니다(SpringConstraintValidatorFactory 덕분입니다).
      • 단, JPA pre-persist 검증 경로에서는 주입이 안 될 수 있습니다. 이때는 jakarta.persistence.validation.factory를 설정하세요.
    • 교차 필드 검증: 기본 위반을 끄고 특정 필드에 위반을 붙입니다.
    ctx.disableDefaultConstraintViolation()

    2.4 Kotlin 함정

    use-site target

    • Kotlin 2.1까지는 생성자 프로퍼티에 붙인 어노테이션이 파라미터에만 적용됐습니다. 그래서 @field:, @param:, @get:을 명시해야 했습니다.
    • Kotlin 2.2의 새 규칙(param-property)은 파라미터와 프로퍼티/필드에 함께 붙입니다. 다만 2.2의 기본 동작은 경고만 내는 과도기 모드입니다.
    • Spring Initializr는 -Xannotation-default-target=param-property를 기본으로 켭니다(#1666).
    • 예전 동작이 필요하면 -Xannotation-default-target=first-only를 쓰세요.
    • @all:은 아직 프리뷰입니다.
    kotlin {
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict", "-Xannotation-default-target=param-property")
    }
}

    2.5 MVC 메서드 검증·설정

    예외 종류

    • MethodArgumentNotValidException: @Valid @RequestBody나 @ModelAttribute 객체가 검증에 실패할 때 납니다.
    • HandlerMethodValidationException: 파라미터에 직접 붙은 제약(예: @RequestParam @Min(1))이 실패할 때 납니다.
      • Spring 6.1부터는 @Validated 없이도 동작합니다.

    • ResponseEntityExceptionHandler가 두 예외를 모두 처리합니다.

    메시지와 설정

    • 메시지: ValidationMessages.properties나 LocalValidatorFactoryBean.setValidationMessageSource로 정의합니다. 메시지 안에서 {min}, ${validatedValue}를 참조할 수 있습니다.

    • @ConfigurationProperties + @Validated: 중첩 객체까지 검증하려면 @field:Valid가 필요합니다.

      5장 Envers + soft delete
      

      soft delete 구현 방식에 따라 Envers 이력이 어떻게 남는지, 어떤 삭제 경로가 감사를 우회하는지, 운영에서 자주 부딪히는 유니크 제약과 복구 문제를 어떻게 푸는지 다룹니다.
      

      

      이 장의 핵심
        

      • @SQLDelete로 지우면 DEL, 플래그를 직접 바꾸면 MOD로 기록됩니다.
        • 

      • store_data_at_delete=true로 삭제 시점의 데이터를 남깁니다.
        • 

      • 벌크 쓰기와 네이티브 쓰기는 soft delete와 감사를 모두 우회합니다.
        • 

      

      5.1 방식별 REVTYPE
      

      REVTYPE은 Envers가 감사 테이블에 남기는 변경 종류로, 0은 ADD(추가), 1은 MOD(수정), 2는 DEL(삭제)을 뜻합니다.
      

      

      방식remove 시 실행되는 SQLREVTYPE확신도
      


      @SQLDelete + @SQLRestriction커스텀 UPDATEDEL (delete 이벤트가 발생함)높음
      

      직접 deleted = true로 수정일반 UPDATEMOD높음
      

      @SoftDelete (6.4 이상, 7.0부터 TIMESTAMP 지원)DeleteCoordinatorSoft가 UPDATE 실행DEL로 추정(미확인)검증 필요낮음~중간
      
      

      

      

      @SoftDelete가 DEL로 추정되는 이유와 한계
      

        

      • 삭제 경로에서 UPDATE를 실행하므로 DEL로 기록될 것으로 봅니다.
        • 

      • 하지만 이를 확정해 주는 공식 문서나 JIRA 이슈는 찾지 못했습니다.
        • 

      • 정황 증거로, spring-data-jpa #4155에 “@SoftDelete로 삭제할 때 AuditorAware가 호출되지 않는다”는 보고가 있습니다.
        • 

      • 도입하기 전에 REVTYPE을 확인하는 통합 테스트를 반드시 작성하세요.
        • 

      

      

      관련 설정과 제약
      

        

      • DEL 행의 데이터: 기본 설정에서는 DEL 행에 id만 남습니다. store_data_at_delete=true를 권장합니다.
        • 

      • @SoftDelete의 제약:

          

        • strategy는 DELETED, ACTIVE, TIMESTAMP 중 하나입니다.
          • 

        • converter를 TIMESTAMP와 함께 쓰면 UnsupportedMappingException이 납니다. converter는 null을 반환하면 안 됩니다.
          • 

        • 삭제 컬럼은 엔티티 필드로 노출되지 않습니다.
          • 

        • 

      • 7.4의 incubating @Audited: 문서에는 “backward compatible with Hibernate Envers”라고 되어 있지만, 아직 incubating이므로 운영 적용은 보류하세요.
        •

      8장 Kotlin 코루틴 + Spring
      

      코루틴을 Spring MVC, 트랜잭션, 스케줄러, 메시징과 함께 쓸 때 필요한 의존성과 함정, 자주 쓰는 타입과 연산자를 정리합니다. 가상 스레드와 어떻게 나눠 쓸지도 다룹니다.
      

      

      이 장의 핵심
        

      • MVC의 suspend와 Flow에는 kotlinx-coroutines-reactor가 필요하고, 테스트는 asyncDispatch를 거칩니다.
        • 

      • JPA 트랜잭션은 withContext + TransactionTemplate 안에서 끝내고, 그 안에서 suspend하지 않습니다.
        • 

      • 기본은 가상 스레드와 동기 코드로 가고, 코루틴은 fan-out과 스트리밍에만 씁니다.
        • 

      

      8.1 MVC
      

        

      • 필수 의존성: kotlinx-coroutines-reactor가 필요합니다.
        • 

      • 동작 방식: suspend 함수는 Mono로 바뀌어 비동기 요청으로 처리됩니다.
        • 

      • Flow 반환: SSE나 NDJSON이면 스트리밍되고, JSON이면 전부 모은 뒤 응답합니다.
        • 

      • 테스트: asyncDispatch가 필요합니다. 첫 요청에 문서화를 걸면 바디가 빈 스니펫이 생성되니, 문서화는 asyncDispatch 쪽에 거세요.
        • 

      

      val r = mockMvc.perform(RestDocumentationRequestBuilders.get("/members/{id}", 1))
    .andExpect(request().asyncStarted()).andReturn()
mockMvc.perform(asyncDispatch(r)).andExpect(status().isOk)
    .andDo(MockMvcRestDocumentationWrapper.document("member-get", resource("회원 조회")))
      

      8.2 트랜잭션·JPA
      

        

      • suspend + @Transactional: 리액티브 트랜잭션으로 처리되므로 ReactiveTransactionManager가 필요합니다. JPA에서는 사실상 쓸 수 없습니다.
        • 

      • 원인: EntityManager가 ThreadLocal에 묶여 있습니다. 코루틴이 다른 스레드에서 재개되면 트랜잭션을 잃고, LazyInitializationException이 나거나 커밋이 누락됩니다.
        • 

      • 해결: 트랜잭션 블록 안에서는 suspend하지 않습니다.
        • 

      

      suspend fun rename(id: Long, name: String) = withContext(dbDispatcher + PropagationContextElement()) {
    tx.execute { repo.findByIdOrNull(id)!!.also { it.rename(name) }.toDto() }!!
}
      

        

      • HikariCP 풀 고갈: IO 디스패처는 64개까지 병렬 실행하지만 커넥션 풀은 기본 10개입니다. val dbDispatcher = Dispatchers.IO.limitedParallelism(maxPoolSize)로 병렬도를 맞추거나 Semaphore로 제한하세요.
        • 

      

      8.3 스케줄러·이벤트·메시징

        • 

      

      Spring Kafka
      

        

      • 3.2부터 async 반환 타입(CompletableFuture, Mono, suspend)을 지원합니다.
