목차 열기

§ 0

RFC 읽는 법

RFC(Request for Comments)는 IETF와 관련 기관이 펴내는 인터넷 기술 문서 시리즈입니다. 이름과 달리 한번 발행된 RFC는 절대 수정되지 않습니다. 고칠 내용이 생기면 새 번호로 다시 냅니다. 그래서 RFC를 펼치면 가장 먼저 “이 문서가 아직 유효한가”를 확인해야 합니다. HTTP/1.1을 설명하며 RFC 2616을 인용하는 글은 2014년 이후로 낡은 정보입니다.

문서를 열면 확인할 순서

  1. Category: 첫 페이지 왼쪽 위. 표준 트랙(Standards Track)인지, 정보성(Informational)인지 봅니다.
  2. Obsoletes / Updates: 이 문서가 대체하거나 일부 고친 RFC. 반대로 rfc-editor.org 페이지의 Obsoleted by는 이 문서를 대체한 후속 RFC입니다.
  3. Errata: 발행 후 발견된 오류 목록. 구현자라면 꼭 확인합니다.
  4. 요구 수준 키워드: 대문자 MUST, SHOULD, MAY가 필수와 권장을 가릅니다(RFC 2119, 8174).
  5. Security Considerations: 모든 RFC에 있는 절. 구현할 때 빠지기 쉬운 함정 목록으로 읽으면 좋습니다.

상태 표시

인터넷 표준가장 높은 성숙 단계. STD 번호가 붙습니다(예: HTTP 의미론 = STD 97).
제안 표준대부분의 표준이 이 단계에 머뭅니다. 미완성이라는 뜻이 아닙니다.
초안 표준2011년 폐지된 중간 단계. 그때 이 상태였던 문서는 그대로 남아 있습니다.
BCP최선의 현행 실무(Best Current Practice). 운영·설계 권고이며 BCP 번호가 붙습니다.
정보표준이 아닌 정보 제공 문서. 그래도 사실상 표준인 경우가 많습니다(gzip, TOTP).
실험실험 목적의 명세. 실제로 널리 쓰여도 이 상태일 수 있습니다(CT, TCP Fast Open).
Internet-DraftRFC가 아닌 작업 문서. 6개월마다 개정·만료됩니다. 구현 전 최신판 확인이 필요합니다.
만우절매년 4월 1일 발행되는 농담 RFC. 418 상태 코드의 출처이기도 합니다.

§ 2

HTTP

2022년 6월, HTTP 명세가 크게 재편됐습니다. 버전과 무관한 의미론(9110), 캐싱(9111), HTTP/1.1 메시지 문법(9112)이 분리되었고, HTTP/2(9113)와 HTTP/3(9114)는 같은 의미론을 다른 방식으로 실어 나르는 문서가 됐습니다. 상태 코드나 메서드의 의미가 궁금하면 이제 9110 하나만 보면 됩니다.

    4.7계정과 디렉터리

    § 5

    부록: RFC가 아닌 웹 표준

    웹에서 매일 쓰는 기술 중 상당수는 RFC가 아닙니다. 찾아볼 곳을 잘못 짚지 않도록 정리했습니다.

    기술표준 기관RFC와의 관계
    CORS, Fetch, URL, HTML, StreamsWHATWG (Living Standard)출처 개념은 RFC 6454, URL 문법은 3986과 다른 부분이 있음
    CSP, WebAuthn, Service Worker, Permissions PolicyW3CCSP frame-ancestors가 X-Frame-Options(7034) 대체
    OpenID ConnectOpenID FoundationOAuth 2.0(6749)과 JWT(7519) 위에 인증 계층
    FIDO2 / CTAP, 패스키FIDO Alliance + W3CCBOR(8949), COSE(9052) 사용
    OpenAPIOpenAPI Initiativeapi-catalog(9727)로 문서 위치 공개 가능
    JSON Schemajson-schema.orgIETF 초안으로 시작했으나 독립
    GraphQLGraphQL FoundationHTTP 위에서 쓰는 방식은 별도 명세(GraphQL over HTTP)
