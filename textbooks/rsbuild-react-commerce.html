    0장 시작하기

    무엇을 만들고, 어떤 도구를 왜 쓰는지 먼저 봅니다. 도구 이름이 많지만 역할은 네 가지뿐입니다. 묶고, 검사하고, 시험하고, 분석합니다.

    이 장의 핵심

    • 완성품은 상품 목록 → 상세 → 장바구니 → 주문서 → 모의 결제 → 주문 완료까지 이어지는 쇼핑몰입니다. 11장에서 바로 조작해 볼 수 있습니다.
    • Rspack은 코드를 묶는 엔진이고, Rsbuild는 그 엔진에 개발 서버와 기본 설정을 얹은 도구입니다. webpack과 Vite의 자리에 각각 대응합니다.
    • Biome은 린트와 포맷을, Rstest는 단위·컴포넌트 테스트를, Rsdoctor는 번들 분석을 맡습니다.

    0.1 완성 결과 미리보기

    예를 들어 사용자가 디지털 카테고리에서 이어폰을 골라 결제한다고 해 봅시다. 화면은 이렇게 이어집니다.

    1. 상품 목록 /?category=digital&sort=price-asc — 필터와 정렬이 주소에 남습니다. 아래로 내리면 다음 20개를 이어서 불러옵니다.
    2. 상세 /products/p-002 — 목록에서 마우스를 올린 순간 미리 받아 둔 데이터로 바로 뜹니다.
    3. 장바구니 /cart — 수량을 바꾸면 화면이 먼저 바뀌고, 재고가 모자라면 되돌아갑니다.
    4. 주문서 /checkout — 휴대폰 번호·우편번호를 검사하고, 결제 버튼을 두 번 눌러도 주문은 하나만 생깁니다.
    5. 모의 결제 /checkout/pay/ORD-000001 → /checkout/confirm — PG사의 요청 → 인증 → 승인 흐름을 흉내 냅니다.
    6. 주문 완료 /orders/ORD-000001/complete — 새로고침해도 같은 주문이 보이고, 뒤로 가기로 결제 단계에 돌아가지 않습니다.

    이 흐름은 Playwright가 데스크톱과 모바일 두 화면 크기에서 매번 끝까지 눌러 보는 E2E 테스트로 지킵니다(9장). 직접 눌러 보고 싶다면 11장의 라이브 데모로 가세요.

    1.3 rsbuild.config.ts 핵심 옵션

    설정 파일 전체입니다. 30줄 남짓이면 충분합니다. React·TypeScript·CSS·HTML·개발 서버·코드 스플리팅은 Rsbuild가 기본으로 해 주기 때문입니다.

    import { defineConfig } from '@rsbuild/core';
import { pluginReact } from '@rsbuild/plugin-react';
import { pluginTailwindcss } from '@rsbuild/plugin-tailwindcss';
import { RsdoctorRspackPlugin } from '@rsdoctor/rspack-plugin';

// Docs: https://rsbuild.rs/config/
export default defineConfig({
  plugins: [pluginReact(), pluginTailwindcss()],
  html: {
    template: './index.html',
    // 지정하지 않으면 기본값 "Rsbuild App"이 들어간다. JS 없이 읽는 크롤러가 보는 제목이다.
    title: '예제 쇼핑몰',
  },
  output: {
    // 파일 이름에 내용 해시를 넣어 오래 캐시해도 배포 때마다 새 파일을 받게 한다.
    filenameHash: true,
  },
  performance: {
    // 빌드 결과에 gzip 크기를 함께 표시한다.
    printFileSize: { compressed: true },
  },
  server: {
    port: 3000,
  },
  tools: {
    rspack: {
      plugins: [
        // RSDOCTOR=true일 때만 번들 분석 보고서(HTML 한 파일 + JSON)를 만든다.
        process.env.RSDOCTOR === 'true' &&
          new RsdoctorRspackPlugin({
            disableClientServer: true,
            output: {
              mode: 'brief',
              reportDir: '.rsdoctor', // dist에 섞여 배포되지 않게 따로 둔다.
              options: { type: ['html', 'json'] },
            },
          }),
      ],
    },
  },
});
    옵션하는 일예제 앱에서 쓴 이유
    pluginsReact(JSX·Fast Refresh), Tailwind CSS 지원을 켭니다.템플릿이 넣어 준 그대로
    html.template기본 HTML 대신 쓸 템플릿 파일<html lang="ko">와 기본 description이 필요해서
    output.filenameHash파일 이름에 내용 해시를 넣습니다(배포 결과물의 기본값).10장 캐시 전략의 전제라서 명시

    1.4 환경 변수

    예를 들어 API 주소와 "목 서버를 켤지"는 환경마다 다릅니다. 이런 값은 .env 파일에 두고 코드에서는 import.meta.env로 읽습니다.

    # 브라우저 코드에 노출되는 변수는 PUBLIC_ 접두사가 필요하다.
PUBLIC_API_BASE=/api
PUBLIC_API_MOCKING=true

    규칙은 세 가지입니다.

    1. PUBLIC_으로 시작하는 변수만 브라우저 코드에 들어갑니다. Rsbuild가 빌드할 때 값을 글자 그대로 바꿔 넣습니다. 그러니 비밀번호나 API 키를 여기에 두면 누구나 볼 수 있습니다.
    2. --env-mode로 파일을 고를 수 있습니다. rsbuild build --env-mode live는 .env를 읽은 다음 .env.live로 덮어씁니다. 예제 앱은 이 모드로 MSW를 뺀 "실서버용" 빌드를 만듭니다.
    3. 이미 process.env에 있는 값은 파일이 덮어쓰지 않습니다. 측정 스크립트에서 .env.live를 읽게 했는데도 MSW가 빠지지 않았습니다. 앞선 빌드가 PUBLIC_API_MOCKING=true를 이미 process.env에 넣어 두었기 때문입니다.실측 CI에서 셸 변수와 .env가 섞이면 같은 일이 생깁니다.
    # rsbuild build --env-mode live → 실제 API 서버에 붙는 빌드(MSW 제외)
PUBLIC_API_MOCKING=false

    타입스크립트가 변수 이름을 알도록 타입을 적어 둡니다. 오타가 컴파일 오류가 됩니다.

    /// <reference types="@rsbuild/core/types" />

interface ImportMetaEnv {
  readonly PUBLIC_API_BASE: string;
  readonly PUBLIC_API_MOCKING: 'true' | 'false';
}

interface ImportMeta {
  readonly env: ImportMetaEnv;
}

    이 값은 빌드 때 상수로 바뀌기 때문에, 조건문과 합쳐 코드를 통째로 빼는 데에도 씁니다. PUBLIC_API_MOCKING이 'false'면 MSW를 불러오는 import()가 죽은 코드가 되어 번들에서 빠집니다(7장에서 크기를 잽니다).

    import './index.css';
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import { createBrowserRouter } from 'react-router';
import { App } from './app/App';
import { routes } from './app/routes';

// 목 서버(MSW)는 PUBLIC_API_MOCKING=true일 때만 불러온다. false면 번들에서도 빠진다.
async function enableMocking() {
  if (import.meta.env.PUBLIC_API_MOCKING !== 'true') return;
  const { worker } = await import(/* webpackChunkName: "msw" */ './mocks/browser');
  await worker.start({
    onUnhandledRequest: 'bypass',
    quiet: true,
  });
}

    Biome 하나로 서식(포맷), 규칙 검사(린트), import 정렬을 합니다. 에디터에서 저장할 때, 커밋할 때, CI에서 같은 설정으로 세 번 검사합니다.

    이 장의 핵심

    • 설정은 biome.json 하나입니다. recommended 규칙에서 시작해 팀에 필요한 규칙만 더합니다.
    • biome check --write는 고치고, biome ci는 고치지 않고 검사만 합니다. CI에는 ci를 씁니다.
    • Biome은 모든 실수를 잡지 않습니다. 예제에서 배열 인덱스를 key로 쓴 코드는 진단 없이 통과했습니다.

    3장 라우팅

    주소마다 어떤 화면을 보여 줄지 정합니다. 레이아웃은 한 번만 그리고, 페이지 코드는 그 주소에 처음 갈 때 내려받게 나눕니다. 오류가 나도 헤더는 살아 있게 합니다.

    이 장의 핵심

    • React Router 8.4.0의 Data Mode(createBrowserRouter)로 라우트를 객체 배열 하나에 모읍니다. v8부터 react-router-dom은 없고, RouterProvider는 react-router/dom에서 가져옵니다.
    • 라우트에 lazy를 주면 페이지마다 청크가 나뉩니다. 첫 화면은 결제 코드를 한 줄도 받지 않습니다.
    • 에러 경계는 레이아웃 바로 아래(경로 없는 라우트)에 둡니다. 그래야 오류 화면에서도 헤더와 장바구니 버튼이 남습니다.

    3.1 페이지와 레이아웃

    라우트 전체입니다. 맨 바깥 라우트가 레이아웃(RootLayout)이고, 그 아래 경로 없는 라우트가 에러 경계만 맡습니다. 실제 페이지는 그 아래에 있습니다.

    3.2 lazy 코드 스플리팅

    lazy: () => import('...')를 만나면 Rspack이 그 파일과 거기서만 쓰는 코드를 따로 떼어 비동기 청크로 만듭니다. webpackChunkName 주석은 청크 이름을 정합니다. Rspack은 webpack의 이 주석 문법을 그대로 이해합니다.

    빌드 결과에서 페이지 청크는 이렇게 나왔습니다.실측 목록 페이지 청크는 gzip 2.8 kB, 주문서 페이지 청크는 2.5 kB입니다. 실제 브라우저로 열어 받은 파일을 기록해 보니:

    • 첫 방문(목록)에는 JS 파일 9개를 받았고 page-checkout.js는 받지 않았습니다.
    • 상세로 가자 page-detail.js 하나만 더 받았습니다.
    • 장바구니를 거쳐 주문서로 가자 page-cart.js, f.js, page-checkout.js를 더 받았습니다. f.js는 React Hook Form이 든 공유 청크입니다.

    이 기록은 e2e/measure.spec.ts가 Playwright로 브라우저의 Resource Timing을 읽어 남긴 것이고, 테스트는 "첫 화면에 결제 코드가 없다"를 확인합니다.

    lazy 경계 시각화

    페이지를 lazy에서 빼면(= 첫 화면 번들에 넣으면) 첫 화면에 받는 JS가 얼마나 늘어나는지 봅니다. 막대 길이는 예제 앱 빌드에서 잰 파일별 gzip 크기입니다.

      항상 받는 초기 청크페이지 청크(목록 + 첫 화면에 넣은 페이지)

      "첫 화면에 넣기"는 각 페이지와 그 페이지만 쓰는 공유 청크 크기를 더한 추정입니다. 실제로 eager import로 바꾸면 공유 모듈의 배치가 달라져 수 kB 차이가 날 수 있습니다.

      HydrateFallback

      처음 열 때 첫 페이지도 lazy라서, 그 코드를 받는 동안 보여 줄 화면이 필요합니다. 없으면 React Router가 "No HydrateFallback element provided" 경고를 냅니다. 테스트 로그에서 이 경고를 보고 루트 라우트에 HydrateFallback을 넣었습니다.실측

      4장 서버 상태

      상품과 주문은 서버가 원본이고, 화면에 있는 것은 복사본입니다. 복사본이 언제 낡는지, 언제 다시 받을지, 실패하면 몇 번 다시 시도할지를 TanStack Query에 맡깁니다. 백엔드 없이도 개발할 수 있게 MSW가 서버 역할을 합니다.

      이 장의 핵심

      • staleTime은 "다시 요청하지 않는 시간", gcTime은 "아무도 안 쓸 때 캐시에 남기는 시간"입니다. 둘은 다른 시계입니다.
      • 필터·정렬·불러온 페이지 수는 URL 상태로 둡니다. 새로고침·공유·뒤로 가기가 공짜로 됩니다.
      • 재시도는 "다시 보내도 결과가 같은 요청"에만 합니다. 4xx는 재시도하지 않고, 간격은 지수 백오프 + 지터로 벌립니다.
      • 모든 요청에 타임아웃을 겁니다. 타임아웃은 실패가 아니라 "결과를 모름"입니다.

      4.1 TanStack Query 기본값

      예를 들어 사용자가 상품 목록을 보다가 상세에 갔다가 10초 만에 돌아온다고 해 봅시다. 목록을 다시 받아야 할까요? 가격이 10초 사이에 바뀔 일은 드뭅니다. 그래서 30초 동안은 fresh로 보고 다시 요청하지 않게 했습니다.

      4.2 URL 상태: 필터·정렬·페이지

export function useInfiniteScroll(onReachEnd: () => void, enabled: boolean) {
  const ref = useRef<HTMLDivElement>(null);
  const callback = useRef(onReachEnd);
  callback.current = onReachEnd;

  useEffect(() => {
    const el = ref.current;
    if (!el || !enabled) return;
    const observer = new IntersectionObserver(
      (entries) => {
        if (entries.some((e) => e.isIntersecting)) callback.current();
      },
      { rootMargin: '400px 0px' },
    );
    observer.observe(el);
    return () => observer.disconnect();
  }, [enabled]);

  return ref;
}

      4.5 재시도와 타임아웃

      모든 요청은 request() 한 함수를 지나갑니다. 여기서 세 가지를 정합니다.

      const API_BASE = import.meta.env.PUBLIC_API_BASE;
const DEFAULT_TIMEOUT_MS = 8000;

export class HttpError extends Error {
  constructor(
    readonly status: number,
    readonly code: string,
    message: string,
    readonly body?: unknown,
  ) {
    super(message);
    this.name = 'HttpError';
  }
}

type RequestOptions = {
  method?: 'GET' | 'POST' | 'PUT' | 'DELETE';
  body?: unknown;
  headers?: Record<string, string>;
  signal?: AbortSignal;
  timeoutMs?: number;
};

export async function request<T>(path: string, options: RequestOptions = {}): Promise<T> {
  const { method = 'GET', body, headers, signal, timeoutMs } = options;
  // TanStack Query가 넘겨준 취소 신호와 타임아웃 신호 중 먼저 오는 쪽으로 요청을 끊는다.
  const timeout = AbortSignal.timeout(timeoutMs ?? DEFAULT_TIMEOUT_MS);
  const res = await fetch(`${API_BASE}${path}`, {
    method,
    headers: {
      ...(body === undefined ? {} : { 'Content-Type': 'application/json' }),
      ...headers,
    },
    body: body === undefined ? undefined : JSON.stringify(body),
    signal: signal ? AbortSignal.any([signal, timeout]) : timeout,
  });
  const data: unknown = res.status === 204 ? null : await res.json();
  if (!res.ok) {
    const problem = (data ?? {}) as { code?: string; message?: string };
    throw new HttpError(
      res.status,
      problem.code ?? 'UNKNOWN',
      problem.message ?? `요청이 실패했습니다 (${res.status})`,
      data,
    );
  }
  return data as T;
}

// 4xx는 다시 보내도 결과가 같으므로 재시도하지 않는다. 408·429와 5xx, 네트워크 오류만 재시도한다.
export function isRetryable(error: unknown): boolean {
  if (error instanceof HttpError) {
    return error.status === 408 || error.status === 429 || error.status >= 500;
  }
  return true;
}

// 지수 백오프(1초, 2초, 4초… 최대 8초)에 지터를 섞어 여러 사용자의 재시도가 한꺼번에 몰리지 않게 한다.
export function retryDelay(attempt: number, random = Math.random): number {
  const base = Math.min(1000 * 2 ** attempt, 8000);
  return Math.round(base / 2 + (base / 2) * random());
}
      1. 타임아웃 — AbortSignal.timeout과 TanStack Query가 넘긴 취소 신호를 AbortSignal.any로 합쳐, 먼저 오는 쪽에서 끊습니다. 사용자가 페이지를 떠나도, 8초가 지나도 요청이 멈춥니다.
      2. 재시도 대상 — 400·404·409·422는 다시 보내도 같은 답이 오므로 재시도하지 않습니다. 408·429·5xx와 네트워크 오류만 재시도합니다.

      장바구니는 브라우저가 들고 있는 상태입니다. 새로고침해도, 다른 탭에서 바꿔도 같아야 합니다. 수량을 바꾸면 화면은 바로 바뀌고, 서버가 재고 부족으로 거절하면 조용히 되돌아가야 합니다.

      이 장의 핵심

      • 클라이언트 상태는 Zustand에, 서버 상태는 TanStack Query에 둡니다. 장바구니 목록은 앞쪽, 재고 확인은 뒤쪽입니다.
      • Zustand의 persist로 localStorage에 저장하고, storage 이벤트로 다른 탭과 맞춥니다.
      • 낙관적 업데이트는 "이전 값 저장 → 화면 먼저 변경 → 실패하면 복원" 세 단계입니다. 같은 대상의 변경은 순서대로 실행해야 롤백이 서로 덮어쓰지 않습니다.
      • 금액은 원 단위 정수로만 계산하고, 화면에 보일 때만 Intl.NumberFormat('ko-KR')으로 바꿉니다.

      5.1 Zustand persist

      import { create } from 'zustand';

import { safeLocalStorage } from '@/shared/lib/storage';

export type CartLine = {
  productId: string;
  name: string;
  price: number;
  imageUrl: string;
  quantity: number;
};

  lines: CartLine[];
  setLine: (line: CartLine) => void;
  remove: (productId: string) => void;
  clear: () => void;
};

export const CART_STORAGE_KEY = 'commerce-cart';

export const useCartStore = create<CartState>()(
  persist(
    (set) => ({
      lines: [],
      setLine: (line) =>
        set((s) => {
          const exists = s.lines.some((l) => l.productId === line.productId);
          return {
            lines: exists
              ? s.lines.map((l) => (l.productId === line.productId ? line : l))
              : [...s.lines, line],
          };
        }),
      remove: (productId) =>
        set((s) => ({ lines: s.lines.filter((l) => l.productId !== productId) })),
      clear: () => set({ lines: [] }),
    }),
    {
      name: CART_STORAGE_KEY,
      version: 1,
      storage: createJSONStorage(() => safeLocalStorage),
      partialize: (s) => ({ lines: s.lines }),

  ),

      5.3 낙관적 업데이트와 롤백

      수량을 5로 바꾸었는데 서버 응답을 기다리느라 0.3초 동안 숫자가 안 바뀌면 사용자는 다시 누릅니다. 그래서 화면을 먼저 바꿉니다. 대신 서버가 "재고가 2개 남았습니다"라고 거절하면 원래 값으로 돌려놓아야 합니다.

      import { useMutation } from '@tanstack/react-query';
import { useState } from 'react';
import { HttpError, request } from '@/shared/lib/http';
import { type CartLine, useCartStore } from './store';

type Vars = { line: Omit<CartLine, 'quantity'>; quantity: number };

// 화면을 먼저 바꾸고(낙관적 업데이트) 서버가 거절하면 이전 상태로 되돌린다.
export function useCartMutation() {
  const [error, setError] = useState<string | null>(null);
  const mutation = useMutation({
    // 같은 scope의 변경은 순서대로 하나씩 실행된다. 롤백이 서로 덮어쓰지 않게 한다.
    scope: { id: 'cart' },
    mutationFn: ({ line, quantity }: Vars) =>
      request(`/cart/items/${line.productId}`, {
        method: 'PUT',
        body: { quantity },
      }),
    onMutate: ({ line, quantity }) => {
      setError(null);
      const { lines, setLine } = useCartStore.getState();
      const previous = lines.find((l) => l.productId === line.productId);
      setLine({ ...line, quantity });
      return { previous };
    },
    onError: (err, { line }, result) => {
      const { setLine, remove } = useCartStore.getState();
      if (result?.previous) setLine(result.previous);
      else remove(line.productId);
      setError(err instanceof HttpError ? err.message : '장바구니를 바꾸지 못했습니다.');
    },
  });
  return { ...mutation, error };
}
      1. onMutate — 바꾸기 전 줄(previous)을 꺼내 두고 화면을 새 수량으로 바꿉니다. 반환값은 나중에 onError가 받습니다.

      3. onError — 이전 줄이 있었으면 되돌리고, 없던 상품이면 지웁니다. 사용자에게는 서버가 보낸 이유를 보여 줍니다.

        5.4 금액 계산

        자바스크립트에서 0.1 + 0.2는 0.30000000000000004입니다. 원화는 소수점이 없으니 처음부터 정수만 씁니다. 배송비 규칙(5만 원 이상 무료, 아니면 3,000원)도 같은 함수에 둡니다. 서버도 이 함수로 주문 금액을 다시 계산합니다(6장).

        export const FREE_SHIPPING_THRESHOLD = 50_000;
export const SHIPPING_FEE = 3_000;

export type PricedLine = { price: number; quantity: number };

export type Totals = { subtotal: number; shippingFee: number; total: number };

// 부동소수점 오차가 없도록 원 단위 정수끼리만 더하고 곱한다.
export function calcTotals(lines: PricedLine[]): Totals {
  const subtotal = lines.reduce((sum, l) => sum + l.price * l.quantity, 0);
  const shippingFee = subtotal === 0 || subtotal >= FREE_SHIPPING_THRESHOLD ? 0 : SHIPPING_FEE;
  return { subtotal, shippingFee, total: subtotal + shippingFee };
}

        표시는 한 함수에서만 합니다. 정수가 아닌 값이 들어오면 조용히 반올림하지 않고 오류를 던져 버그를 빨리 드러냅니다.

        // 금액은 항상 "원" 단위 정수로 다루고, 화면에 보일 때만 문자열로 바꾼다.

        6.2 PG 결제 흐름: 요청 → 인증 → 승인

        국내 PG의 일반적인 흐름을 흉내 냈습니다. 실제 PG SDK는 결제창을 PG사 도메인에 띄우지만, 예제는 앱 안의 모의 결제창으로 대신합니다.

        1. 요청 — 주문서가 POST /api/orders로 주문을 만듭니다. 서버는 클라이언트가 보낸 금액을 믿지 않고 상품 가격으로 다시 계산해 PENDING_PAYMENT 주문을 돌려줍니다.
        2. 인증 — 결제창(/checkout/pay/:orderId)에서 사용자가 카드 인증을 합니다. 끝나면 PG가 paymentKey, orderId, amount를 붙여 우리 페이지로 돌려보냅니다.
        3. 승인 — 돌아온 페이지(/checkout/confirm)가 서버에 POST /api/payments/confirm을 보냅니다. 서버는 주문 금액과 amount가 같은지 확인한 뒤에야 결제를 확정합니다. 주소의 금액은 사용자가 고칠 수 있기 때문입니다.

            // Rsdoctor JSON에서 청크마다 어떤 패키지가 들어 있는지 뽑는다.
function composition() {
  const { data } = JSON.parse(readFileSync('.rsdoctor/rsdoctor-data.json', 'utf8'));
  const byId = new Map(data.moduleGraph.modules.map((m) => [m.id, m]));
  const pkgOf = (path) => {
    const m = path.match(/node_modules\/((?:@[^/]+\/)?[^/]+)/);
    return m ? m[1] : path.includes('/src/') ? 'src' : 'other';
  };
  return data.chunkGraph.chunks.map((c) => {
    const pk = {};
    for (const id of c.modules) {
      const m = byId.get(id);
      if (!m) continue;
      const k = pkgOf(m.path);
      pk[k] = (pk[k] ?? 0) + (m.size?.parsedSize ?? 0);
    }
    const packages = Object.entries(pk)
      .sort((a, b) => b[1] - a[1])
      .map(([name, parsed]) => ({ name, parsed }));
    return { name: c.name || c.id, initial: c.initial, assets: c.assets, packages };
  });
}

              Core Web Vitals는 LCP(2.5초 이하), INP(200ms 이하), CLS(0.1 이하) 세 가지입니다. 기준은 실제 사용자 데이터의 75번째 백분위입니다. 로컬에서 Playwright로 잰 값은 참고용입니다. 예제 앱의 목록 첫 화면은 LCP 380 ms, CLS 0였습니다.실측 이 값에는 MSW 워커를 등록하는 시간이 포함되어 있습니다. E2E는 CLS가 0.1 미만인지 확인합니다.

              INP는 사용자의 실제 상호작용이 있어야 잴 수 있어 로컬 측정에서 뺐습니다. 운영에서는 web-vitals 라이브러리로 실제 사용자 값을 모으세요.

              7.6 가상 스크롤

              8장 렌더링과 SEO

              예제 앱은 CSR입니다. 브라우저가 JS를 받아 실행해야 화면이 생깁니다. 쇼핑몰에서 이것이 언제 문제가 되는지, 메타 태그와 구조화 데이터로 무엇을 할 수 있는지, 언제 SSR·SSG로 가야 하는지 봅니다.

              이 장의 핵심

              • CSR 앱의 HTML에는 본문이 없습니다. JS를 실행하지 않는 크롤러와 링크 미리보기는 빈 페이지를 봅니다.
              • React 19는 컴포넌트 안의 <title>·<meta>를 <head>로 옮겨 줍니다. 라이브러리 없이 페이지마다 제목을 바꿀 수 있습니다.
              • 상품 상세에는 JSON-LD(schema.org Product)를 넣어 가격·재고를 검색 엔진에 알립니다.
              • 검색 유입이 중요한 목록·상세는 SSR·SSG를, 로그인 뒤의 장바구니·주문은 CSR을 고르는 식으로 화면마다 나눠 생각합니다.

}

              9장 테스트

              테스트를 세 층으로 나눕니다. 금액 계산 같은 순수 함수는 단위 테스트로, 화면과 서버가 만나는 곳은 컴포넌트 테스트로, 구매 흐름 전체는 E2E로 지킵니다. 세 층 모두 같은 MSW 핸들러를 씁니다.

              이 장의 핵심

              • Rstest는 withRsbuildConfig()로 앱의 빌드 설정(별칭, 환경 변수, 플러그인)을 그대로 물려받습니다. 테스트용 설정을 따로 맞출 필요가 없습니다.

              도우미는 실제 routes를 createMemoryRouter로 띄우고, 재시도를 끈 QueryClient를 넣습니다. 재시도가 켜져 있으면 실패 테스트가 몇 초씩 기다립니다.

              import { QueryClient, QueryClientProvider } from '@tanstack/react-query';

// 실제 routes를 메모리 라우터로 띄워 URL부터 화면까지 한 번에 검사한다.
export function renderRoute(path: string) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false }, mutations: { retry: false } },
  });
  const router = createMemoryRouter(routes, { initialEntries: [path] });
  render(
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>,
  );
  return { router, queryClient };
}

              10장 배포

              dist/ 폴더는 정적 파일뿐이라 어느 정적 호스팅에나 올릴 수 있습니다. 문제는 두 가지입니다. SPA 주소로 새로고침했을 때 404가 나는 것, 그리고 새 버전을 배포했는데 사용자가 옛 파일을 계속 쓰는 것입니다.

              이 장의 핵심

              • SPA는 /cart 같은 주소에 실제 파일이 없습니다. 서버가 없는 주소에 index.html을 돌려주도록(SPA 폴백) 해야 새로고침이 됩니다.
              • Cloudflare Pages는 최상위 404.html이 없으면 SPA로 보고 모든 경로를 /로 연결합니다. GitHub Pages는 없는 경로에 404를 돌려줍니다.
              • 해시가 붙은 파일은 max-age=31536000, immutable로 1년, index.html은 no-cache로 매번 확인합니다.

              10.1 정적 배포

              빌드 결과는 이렇게 생겼습니다. 파일 이름의 해시는 내용이 바뀔 때만 바뀝니다.

              10.2 SPA 새로고침 404

              사용자가 /orders/ORD-000001/complete에서 새로고침하면 브라우저는 서버에 그 경로의 파일을 달라고 합니다. 그런 파일은 없습니다. 앱 안에서 링크로 이동할 때는 React Router가 주소만 바꾸므로 괜찮았던 것입니다.

              • Cloudflare Pages — 아무것도 하지 않아도 됩니다. 다만 404.html을 만들면 SPA 동작이 꺼지니 주의하세요.
              • GitHub Pages — 흔히 빌드 뒤 index.html을 404.html로 복사합니다. 화면은 뜨지만 응답 상태는 404이므로 검색 엔진에는 "없는 페이지"로 보입니다.검증 필요 공개 상품 페이지가 중요하다면 GitHub Pages보다 SPA 폴백을 지원하는 호스팅을 고르세요.
              • 개발·미리보기 서버 — Rsbuild의 개발 서버와 rsbuild preview는 기본으로 폴백합니다. 그래서 E2E의 "완료 페이지에서 새로고침"이 통과합니다. 로컬에서 통과했다고 호스팅에서도 된다는 뜻은 아닙니다.

              10.3 캐시 헤더

              규칙은 "이름이 곧 버전인 파일은 영원히, 이름이 안 바뀌는 파일은 매번 확인"입니다. 예제 앱은 Cloudflare Pages용 public/_headers를 두었습니다. public/의 파일은 빌드할 때 dist/로 그대로 복사됩니다.

              • index.html — 이 파일이 새 해시 이름들을 가리키는 "목차"입니다. 이것이 캐시되면 새 배포가 보이지 않습니다. no-cache는 "저장은 하되 쓰기 전에 서버에 확인"입니다(no-store와 다릅니다).
              • mockServiceWorker.js — 해시가 없으니 HTML과 같은 취급입니다.
