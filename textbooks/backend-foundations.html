    시작하기 — 이 책으로 무엇을 할 수 있게 되나

    이 책은 “어떤 제품을 쓰면 되나”보다 “지금 무엇이 막혀 있고, 무엇을 확인해야 후보를 고를 수 있나”를 연습합니다. 요청 하나가 서버와 DB를 지나가는 원리에서 출발해, 작은 실험으로 실패를 재현하고, 조건이 바뀌었을 때 설계를 다시 고르는 데까지 갑니다.

    이 장의 핵심

    • 목표는 해법의 이름을 빨리 떠올리는 것이 아니라, 증상을 쪼개고 데이터의 성격을 확인해 후보를 만드는 과정입니다.
    • 한 장은 원리 연결 → 실패 재현 → 판단 전이의 세 단계로 공부합니다.
    • 본문 사례의 트래픽·지연·비용은 모두 학습용 가정입니다. 실제로 잰 값과 나눠서 읽으세요.

    출발점이 된 질문

    “쓰기 부하 때문에 DynamoDB를 도입했고, Write IOPS를 75% 줄였다.”

    다른 개발자의 이력서에서 이 문장을 읽었습니다. 같은 상황이었다면 나는 왜 샤딩밖에 떠올리지 못했을까요?

    해법의 이름을 몰랐을 수도 있습니다. 하지만 이 책이 더 중요하게 보는 차이는 다른 데 있습니다. 증상을 쪼개고, 데이터가 어떤 성격인지 확인하고, 그 결과로 후보를 만드는 과정입니다. 제품 이름을 먼저 떠올리는 속도는 학습 목표로 삼지 않습니다.

    1. 증상 쪼개기

      무엇이 늘었나요? 요청 수, 데이터 크기, 쓰기 한 번의 비용, 특정 키로의 쏠림 중 무엇인가요?

    2. 데이터 성격 확인

      잃어도 되나요? 늦게 반영돼도 되나요? 과거 값을 모두 남겨야 하나요?

    3. 후보 만들기

      기존 DB 개선, 쓰기 합치기, 샤딩, 다른 저장소 분리를 같은 조건에서 나란히 놓습니다.

    4. 작게 검증하기

      무엇을 재고, 어떤 결과가 나오면 그 후보를 버릴지 먼저 적습니다.

    사례의 숫자는 가정입니다. 본문의 서비스 이름, 트래픽, 지연과 비용 조건은 모두 학습용 가정입니다. 이력서 주인의 실제 사실처럼 읽지 마세요. 실험도 “예상되는 경향”과 “이 환경에서 실제로 실행한 결과”를 나눠 적습니다.

    이 책의 구성

    처음 배운다면 1~4장을 순서대로 읽습니다. 그다음 이력서 사례가 궁금하면 5~6장, 중복 처리와 장애 대응이 궁금하면 7~9장으로 갑니다. 10장은 앞의 판단을 문서와 검증 절차로 마무리합니다. 참고편을 처음부터 외울 필요는 없습니다.

    먼저 익힐 단위와 용어

    책 전체에서 계속 쓰는 말입니다. 뜻과 함께 작은 예시를 붙였습니다.

    ms와 s
    밀리초와 초. 1초는 1,000ms입니다. 250ms는 0.25초입니다.
    RPS와 TPS
    초당 요청 수와 초당 트랜잭션 수. 요청 하나가 트랜잭션을 여러 개 만들 수 있어서 같은 단위가 아닙니다.
    p95와 p99
    관측값의 약 95%(99%)가 이 값 이하인 지점. 응답 100개를 빠른 순으로 세우면 95번째 값이 p95입니다. 평균이나 최댓값이 아닙니다.
    지연과 처리량
    일 하나가 끝나기까지 걸린 시간과 단위 시간에 끝낸 일의 양. 계산대에서 손님 한 명이 3분 걸리는 것과, 계산대 네 곳이 1시간에 80명을 처리하는 것은 서로 다른 값입니다.
    원자성
    묶인 작업이 일부만 반영되지 않는 성질. 이체에서 출금만 되고 입금이 빠진 상태가 남지 않습니다.
    내구성
    성공한 결과가 약속한 장애 조건에서 살아남는 성질. “어떤 장애까지?”라는 질문이 늘 따라붙습니다.
    불변식
    실행 순서와 실패가 어떻게 섞여도 지켜야 할 업무 규칙. 예: 참여 신청은 사용자·챌린지마다 한 번뿐입니다.
    가설과 관측
    검증할 설명과 실제로 잰 결과. “DB가 느려졌다”는 가설이고, “SQL 실행 p95가 20ms에서 180ms로 늘었다”는 관측입니다.

    1장 요청 하나가 지나가는 길

    촬영 상태를 저장하는 요청 하나를 처음부터 끝까지 따라갑니다. 어디서 계산하고 어디서 기다리는지, 어디서 끊기면 결과를 알 수 없게 되는지 표시할 수 있으면 이 장을 마친 것입니다.

    이 장의 핵심

    • 요청은 여러 경계를 지나고, 경계마다 기다리거나 실패할 수 있습니다.
    • CPU가 바쁘면 계산을, CPU가 한가한데 느리면 대기를 의심합니다. 다만 CPU가 낮다는 사실만으로 원인을 정하지 않습니다.
    • 스레드를 늘려도, 가상 스레드를 써도 DB 연결 같은 희소 자원의 한도는 늘지 않습니다.
    • 클라이언트의 타임아웃은 “결과를 모른다”는 뜻이지 “저장에 실패했다”는 뜻이 아닙니다.

    1.1 먼저 알아둘 말

    클라이언트와 서버
    일을 요청하는 쪽과, 요청을 받아 처리하는 쪽입니다. 둘이 주고받는 메시지가 요청과 응답입니다.
    프록시
    둘 사이에서 요청을 대신 전달하는 중간자입니다. 로드 밸런서나 API 게이트웨이가 여기에 해당합니다.
    호스트 이름
    사람이 쓰는 서버 이름입니다. api.example.com처럼 씁니다.
    연결과 소켓
    연결은 두 프로그램이 데이터를 주고받으려고 유지하는 통신 경로이고, 소켓은 프로그램이 그 경로를 다루는 운영체제의 창구입니다.
    POST
    HTTP 요청의 한 종류입니다. 여기서는 촬영 상태를 서버에 보낼 때 씁니다.
    프로그램·프로세스·스레드
    프로그램은 저장된 명령과 데이터, 프로세스는 운영체제가 그 프로그램을 실행하는 단위(자기 주소 공간을 가짐), 스레드는 프로세스 안의 실행 흐름입니다.

    같은 프로세스의 스레드는 메모리를 공유합니다. 그래서 한 요청이 쓰던 데이터를 다른 요청이 실수로 바꿀 수 있습니다. 이 문제는 4장에서 다룹니다.

    서버의 자원은 네 가지로 나눠 생각합니다. CPU는 명령을 실행하고, 메모리는 실행 중인 코드와 데이터를 담고, 디스크는 전원이 꺼져도 남겨야 할 데이터를 저장하고, 네트워크는 다른 프로세스·컴퓨터와 정보를 주고받습니다. 서버 성능은 이 자원들의 속도뿐 아니라 자원을 얻으려고 기다리는 시간에도 좌우됩니다. 이 장의 거의 모든 내용이 이 한 문장에서 나옵니다.

    1.2 POST 요청 하나를 따라가기

    촬영 앱이 “녹화 중” 상태를 서버에 저장한다고 합시다. 클라이언트는 호스트 이름을 주소로 바꾸고(DNS 조회), 연결을 새로 만들거나 이미 있는 연결을 다시 씁니다. HTTPS라면 TLS로 서버가 진짜인지 확인하고 통신을 암호화합니다. 요청이 프록시를 거쳐 서버에 도착하면, 서버는 인증 → 입력 검증 → 업무 처리 → 저장을 거쳐 응답합니다.

      매번 하지 않는 일이 있다

      DNS 조회와 연결 수립은 요청마다 반복되지 않습니다. 조회 결과는 캐시되고, 연결은 재사용되기 때문입니다. 새 연결이라면 TCP 연결에 왕복 한 번, TLS 1.3 핸드셰이크에 왕복 한 번이 들어서, 요청을 보내기까지 대략 두 번의 왕복(RTT)이 먼저 필요합니다.보강 탐색기에서 ‘다음 요청’을 고르면 이 단계들이 흐려지는 것을 볼 수 있습니다.

      그래서 “첫 요청만 느리다”와 “모든 요청이 느리다”는 서로 다른 가설로 이어집니다. 앞의 것은 이름 조회·연결 수립 쪽을, 뒤의 것은 서버 안의 처리나 대기를 먼저 봅니다. 또 한 사용자의 요청이 빨라 보여도 다른 사용자는 풀이나 큐에서 오래 기다리고 있을 수 있습니다.

      바이트와 다섯 가지 사건

      네트워크로 받는 것은 ‘객체’가 아니라 바이트입니다. HTTP와 JSON 같은 형식이 그 바이트의 의미를 정합니다. 아래 다섯 사건은 모두 다른 시점에 일어납니다.

      1. 네트워크 수신 완료
      2. 요청 파싱 완료
      3. 업무 처리 완료
      4. DB 커밋 완료
      5. 클라이언트가 응답을 받음

      ③까지 끝났는데 ④ 전에 서버가 죽을 수도 있고, ④까지 끝났는데 ⑤가 일어나지 않을 수도 있습니다. 특히 ④와 ⑤ 사이에서 끊기면 서버에는 저장됐는데 클라이언트는 그 사실을 모릅니다. 이 장 끝의 연습 1과 7장의 멱등성이 바로 이 틈을 다룹니다.

      1.3 계산과 대기를 구분하기

      느려진 서버를 보면 먼저 “CPU가 일을 많이 하나, 아니면 무언가를 기다리나”를 나눕니다.

      관찰먼저 의심할 것
      CPU가 바쁘고 느리다계산 암호화, 압축, JSON 파싱, 비싼 반복문
      CPU는 한가한데 느리다대기 네트워크, DB 락, 커넥션 풀, 디스크, 실행 순서를 기다리는 스케줄링 대기

      CPU가 낮다고 네트워크 탓은 아닙니다. CPU가 낮다는 사실은 “계산 병목은 아닐 수 있다”까지만 알려 줍니다. 락, 풀, 디스크 대기도 똑같이 CPU를 쓰지 않습니다. 반대로 전체 CPU 평균은 일부 코어의 포화를 숨길 수 있습니다.

      스레드를 늘려도 DB 작업은 늘지 않는다

      스레드를 늘리면 여러 작업이 기다리는 시간을 겹칠 수 있습니다. 하지만 DB 연결 20개가 모두 쓰이는 중이라면, 요청 스레드를 2,000개 만들어도 DB 작업은 동시에 20개까지만 진행됩니다. 나머지는 줄을 섭니다. 기다리는 요청도 메모리를 차지하고, 오래 기다리면 타임아웃이 납니다.

      테이블이 20개인 식당을 떠올려 보세요. 대기표를 2,000장 나눠 줘도 동시에 식사하는 손님은 20팀입니다. 대기표를 더 찍는다고 테이블이 늘지는 않습니다.

      가상 스레드는 기다리는 실행 흐름을 싸게, 많이 다룰 수 있게 해 주는 도구입니다. CPU, DB 연결, 외부 API의 호출 한도를 늘려 주지는 않습니다. JDK 24에서 synchronized 블록 때문에 가상 스레드가 캐리어 스레드에 묶이던 pinning 문제가 크게 개선됐습니다(JEP 491). 하지만 그 개선과 상관없이 희소 자원의 동시 사용량은 따로 제한해야 합니다. 개선된 범위를 “모든 pinning이 사라졌다”로 넓혀 읽지도 않습니다.S12

      Spring Boot 4 · Kotlin에서는보강 가상 스레드를 켜는 설정과 DB 동시 작업의 상한은 서로 다른 줄입니다. 앞의 것을 켜도 뒤의 값은 그대로입니다.

      spring:
  threads:
    virtual:
      enabled: true            # 요청 처리에 가상 스레드를 쓴다
  datasource:
    hikari:
      maximum-pool-size: 20    # DB 작업의 동시 실행 상한은 여전히 이 값이다
      connection-timeout: 3000 # 연결을 기다리는 최대 시간(ms). 기본값은 30000

      HikariCP 지표를 Micrometer로 보면 대기가 숫자로 보입니다. hikaricp.connections.pending은 연결을 기다리는 요청 수, hikaricp.connections.acquire는 연결을 얻기까지 걸린 시간, hikaricp.connections.usage는 연결을 빌려 쓴 시간입니다. 아래 800ms 예제의 ‘풀 대기’가 acquire 시간으로 나타납니다.

      1.4 운영체제까지 내려가 보기

      애플리케이션이 파일이나 소켓을 쓰려면 운영체제 기능을 호출합니다. 이것이 시스템 콜입니다. 컨텍스트 스위치는 CPU가 실행 중인 작업의 상태를 보관하고 다른 작업으로 바꾸는 일입니다. 둘은 같은 사건이 아닙니다. 이미 도착한 데이터를 읽는 시스템 콜은 곧바로 돌아오고, 읽을 데이터가 없어 기다려야 할 때에야 스레드가 잠들고 다른 작업으로 전환될 수 있습니다.

      프로그램이 보는 메모리 주소도 실제 메모리의 주소가 아닙니다. 운영체제가 가상 주소를 물리 메모리에 연결해 줍니다. 접근한 페이지가 아직 준비되지 않았으면 페이지 폴트가 납니다. 그런데 모든 페이지 폴트가 디스크 접근은 아닙니다. 이미 메모리에 있는 페이지를 연결만 하면 되는 minor fault와, 디스크에서 읽어 와야 하는 major fault가 있습니다.S25

      관찰뜻바로 내리면 안 되는 결론
      시스템 콜이 많다운영체제 기능을 자주 부른다“컨텍스트 스위치가 많다”
      페이지 폴트가 많다준비 안 된 페이지에 자주 접근한다“디스크가 느리다”(minor fault는 디스크를 읽지 않음)

      1.6 연습

      연습 1서버가 저장을 마친 뒤 응답을 보내기 직전에 연결이 끊겼습니다. 클라이언트의 타임아웃은 저장 실패를 뜻할까요?

      해설 보기

      아닙니다. 클라이언트가 결과를 확인하지 못했을 뿐, 저장은 끝났을 수 있습니다. 그래서 무작정 다시 저장하면 같은 데이터가 두 번 들어갈 수 있습니다.

      다시 시도하기 전에 “이것이 같은 요청인가”를 알아보고, 이미 처리됐다면 기존 결과를 돌려주는 정책이 필요합니다. 이 문제가 7장의 멱등성으로 이어집니다.

      연습 2CPU 사용률은 20%인데 요청 지연이 3배가 됐습니다. “더 큰 CPU로 바꾸자”는 제안에 어떤 증거를 요구하겠습니까?

      해설 보기

      계산이 병목이라는 증거를 먼저 요구합니다. 코어별 CPU와 컨테이너의 CPU 스로틀링을 보고, 함께 DB·네트워크 시간, 풀 대기, 락 대기, 요청량을 봅니다.

      전체 CPU 평균은 일부 코어의 포화를 숨길 수 있습니다. 8코어 중 한 코어만 100%로 바쁘면 평균은 약 12.5%입니다. 더 큰 CPU가 틀렸다고 단정하기보다, 그 변경으로 어떤 대기가 줄어들지 설명할 수 있는지 확인합니다.

      스스로 점검

      2장 SQL 한 번과 디스크 쓰기 한 번은 다르다

      “쓰기 부하가 크다”는 말을 요청 수, SQL 수, WAL 양, IOPS, 지연으로 쪼개 봅니다. COMMIT 한 번이 메모리와 디스크에서 무엇을 하는지 알면, 숫자 하나로 개선을 단정하지 않게 됩니다.

      이 장의 핵심

      • IOPS는 초당 입출력 작업 횟수입니다. 옮긴 데이터 양(처리량)이나 한 번에 걸린 시간(지연)과 다른 값입니다.
      • COMMIT이 성공을 알리기 전에 필요한 것은 WAL의 영속화입니다. 테이블·인덱스 페이지는 나중에 따로 기록될 수 있습니다.
      • 인덱스와 행 버전(MVCC)이 UPDATE 한 번의 일을 늘립니다. 실험 B에서는 같은 UPDATE의 WAL 레코드가 조건에 따라 3배가 됐습니다.
      • 저장 호출을 줄였다는 사실이 곧 IOPS나 비용이 줄었다는 뜻은 아닙니다.

      저장과 영속화
      저장은 데이터를 어딘가에 두는 일, 영속화는 실행 중인 메모리 밖에 남겨 나중에도 쓸 수 있게 하는 일입니다.
      내구성
      그 결과가 어떤 장애까지 살아남는지에 대한 보장입니다. 프로세스 종료, 서버 전원 장애, 디스크 고장은 서로 다른 장애입니다.
      포화
      처리 여유가 모자라 대기나 거절이 생기는 상태입니다.
      병목
      전체 진행 속도를 제한하는 단계입니다. 병목이 아닌 곳을 빠르게 해도 전체는 빨라지지 않습니다.

      “부하가 늘었다”고 말할 때는 무엇이 바뀌었는지 붙이세요. 요청 수가 늘었나요, 데이터 하나의 크기가 커졌나요, 아니면 특정 키로 요청이 몰리기 시작했나요? 셋은 해법이 전혀 다릅니다.

      2.2 IOPS를 이름부터 읽기

      IOPS는 Input/Output Operations Per Second의 약어입니다. 조각으로 나눠 읽으면 뜻이 보입니다. Input/Output은 데이터를 읽고 쓰는 입출력, Operations는 작업 횟수, Per Second는 1초당입니다. 합치면 초당 입출력 작업 횟수입니다. DB 저장 성능을 말할 때는 저장 장치나 저장 계층에서 읽고 쓴 작업을 셉니다.S27

      파일을 읽는 일은 읽기 I/O, 변경 내용을 저장 장치에 쓰는 일은 쓰기 I/O입니다. Read IOPS는 초당 읽기 횟수, Write IOPS는 초당 쓰기 횟수입니다. 같은 측정 경계와 기간에서 읽기가 초당 300회, 쓰기가 초당 700회라면 합계는 1,000 IOPS입니다. 화면에 보이는 값이 실제로 관측한 횟수인지, 제품에 설정한 처리 한도인지도 확인하세요.

      IOPS는 데이터 크기도, 걸린 시간도 아닙니다. 작은 상자 1,000개와 큰 상자 1,000개를 옮기면 횟수는 같지만 옮긴 양은 다릅니다. 상자 하나가 도착하기까지 걸린 시간은 또 다른 값입니다. 그래서 세 가지 질문을 따로 묻습니다.

      질문지표와 예읽는 법
      몇 번 처리했나Write IOPS = 1,000그 경계에서 초당 쓰기 작업 1,000회
      얼마나 많이 옮겼나쓰기 처리량 = 4,000 KiB/s초당 약 3.91 MiB
      하나가 얼마나 걸렸나평균 쓰기 지연 = 2ms작업 하나가 평균 0.002초

      모든 작업이 4 KiB이고 초당 1,000번 처리했다면 처리량은 1,000 × 4 = 4,000 KiB/s입니다. 1 MiB는 1,024 KiB이므로 4,000 ÷ 1,024 ≈ 3.91 MiB/s입니다. 4 KiB는 예로 든 크기일 뿐, I/O 작업 하나의 고정 크기가 아닙니다. 참고로 KiB는 정확히 1,024바이트이고 KB는 보통 1,000바이트입니다. 제품마다 섞어 쓰니 지표 정의를 확인하세요.

      IOPS 계산기

      횟수·시간·크기를 넣으면 IOPS와 처리량을 나눠 계산합니다. 관측 계층이 I/O를 나눠 세는 경우도 확인해 보세요.

      지연의 역수는 한도가 아니다

      평균 쓰기 지연 2ms의 역수인 초당 500회를 시스템 전체의 처리 한도로 쓰면 안 됩니다. 여러 작업이 겹쳐 진행될 수 있기 때문입니다. 동시에 4개씩 겹쳐 처리한다면 4 ÷ 0.002초 = 초당 2,000회까지 가능합니다. 이 관계는 5장의 Little의 법칙으로 다시 봅니다.보강 반대로 설정한 IOPS가 커도, 처리량 한도나 다른 단계의 대기 때문에 실제 처리량은 작을 수 있습니다.

      누가 세느냐에 따라 숫자가 다르다

      관측 계층은 작은 작업을 합치거나 큰 작업을 나눠 셀 수 있습니다. 예를 들어 AWS EBS의 SSD 볼륨은 I/O 하나를 최대 256 KiB로 셉니다. 1,024 KiB짜리 I/O 하나는 256 KiB 네 번으로 나눠 세고, 물리적으로 연속된 32 KiB I/O 여덟 개는 256 KiB 한 번으로 합쳐 셀 수 있습니다.S27보강 계산기에서 ‘1 MiB I/O를 EBS SSD에서’를 눌러 보세요.

      이력서의 “75% 감소” 읽기

      기존 Write IOPS가 4,000이고 변경 뒤 1,000이라면 (4,000 − 1,000) ÷ 4,000 × 100 = 75%입니다. 같은 업무를 더 적은 저장 작업으로 처리했다면 개선의 근거가 됩니다. 하지만 요청이 줄었거나, 저장이 실패했거나, 일을 다른 저장소로 옮겨도 똑같은 숫자가 나옵니다. 이 숫자만으로 전체 비용이나 성능이 좋아졌다고 확정하지 않습니다. 6장에서 이 75%를 검증하는 방법을 다룹니다.

      손으로 풀기10초 동안 쓰기 작업을 20,000번 완료했습니다. 작업 크기가 모두 4 KiB라면 평균 Write IOPS와 쓰기 처리량은 얼마일까요? SQL 실행 횟수도 알 수 있을까요?

      해설 보기

      20,000 ÷ 10 = 2,000 IOPS입니다. 처리량은 2,000 × 4 = 8,000 KiB/s, 약 7.81 MiB/s입니다.

      SQL 실행 횟수는 알 수 없습니다. SQL 하나가 여러 저장 작업을 만들 수도 있고, 여러 SQL의 기록이 합쳐져 한 번에 쓰일 수도 있습니다. 그 사이에 있는 페이지·버퍼·WAL을 다음 절에서 봅니다.

      2.3 행·페이지·버퍼

      SQL은 데이터를 어떻게 다룰지 DB에 전달하는 언어이고, 행은 논리적인 데이터 한 건입니다. 그런데 DB가 디스크와 주고받는 단위는 행이 아니라 페이지입니다. PostgreSQL은 테이블과 인덱스를 페이지 단위로 관리하고, 기본 빌드의 페이지 크기는 8 KiB(8,192바이트)입니다. 문서에 “8kB”로 적힌 것이 이 크기입니다. 그렇다고 한 행을 바꿀 때마다 디스크에 8 KiB를 한 번 쓰는 것은 아닙니다.

      DB는 자주 쓰는 페이지를 메모리의 버퍼에 올려 둡니다. 버퍼에서 내용이 바뀌었지만 아직 데이터 파일에 반영되지 않은 페이지를 dirty page라고 부릅니다. 메모리에서 바꾸는 것은 빠르지만, 프로세스나 서버가 죽으면 사라집니다. 그래서 복구에 쓸 기록이 따로 필요합니다. 그것이 WAL입니다.

      2.4 WAL은 왜 먼저 기록하나

      WAL(Write-Ahead Log)은 데이터 페이지보다 먼저 안전하게 남기는 변경 기록입니다. PostgreSQL은 변경마다 WAL 레코드를 만들고, 그 변경을 복구하는 데 필요한 WAL이 안전해지기 전에는 해당 데이터 페이지를 먼저 디스크에 쓰지 않습니다. 장애가 나면 마지막 checkpoint부터 WAL을 다시 적용해 상태를 되살립니다.S1 규칙은 한 줄입니다. 페이지보다 로그가 먼저.

      COMMIT 한 번 따라가기

      단계를 넘기며 메모리와 디스크에 무엇이 있는지 보세요. 각 단계에서 ‘이 시점에 서버가 죽으면?’을 눌러 결과를 확인합니다.

      synchronous_commit

        PostgreSQL의 일반적인 동작을 단순화했습니다. fsync가 켜져 있고, 저장 장치가 쓰기 완료를 정직하게 보고한다고 가정합니다.

        정리하면, 일반적인 로컬 내구성 설정에서 COMMIT은 필요한 WAL이 영속화되기를 기다린 뒤 성공을 알립니다. 수정한 테이블·인덱스 페이지가 그 순간 모두 디스크에 있어야 하는 것은 아닙니다. 같은 순간에 커밋하는 여러 트랜잭션이 WAL 동기화(fsync) 한 번을 함께 쓸 수도 있습니다. 데이터 페이지는 체크포인트와 백그라운드 작업이 나중에 나눠 기록합니다. 그래서 커밋 수와 디스크 쓰기 횟수는 1:1이 아닙니다.

        설정에 따라 약속이 달라진다

        “커밋했다”가 무엇을 보장하는지는 설정과 저장 장치에 달려 있습니다.S1

        설정성공 응답을 보내는 시점장애가 나면
        synchronous_commit = on (기본값)이 서버의 WAL이 저장 장치에 내려간 뒤성공 응답을 받은 트랜잭션은 복구됩니다.
        synchronous_commit = offWAL 영속화를 기다리지 않고 바로최근에 성공 응답을 받은 트랜잭션 일부가 사라질 수 있습니다. DB가 깨지지는 않고, 그 트랜잭션들이 롤백된 것처럼 됩니다.
        fsync = off보강저장 장치까지 내려보내는 일을 운영체제에 맡김전원·OS 장애 때 복구할 수 없는 데이터 손상이 생길 수 있습니다. 운영 환경에서 끄지 않습니다.
        동기 복제지정한 대기 서버가 정해진 단계(remote_write, on, remote_apply)까지 마친 뒤어느 노드가 어느 단계까지 마쳤는지가 조건입니다.

        “커밋 = 모든 복제본에 저장 완료”가 아닙니다. 비동기 커밋으로 응답을 앞당기면 성공을 받은 최근 트랜잭션이 장애 때 사라질 수 있습니다. 동기 복제를 써도 어떤 원격 노드가 어떤 단계까지 기다리는지 설정을 확인해야 합니다.

        2.5 인덱스와 행 버전이 쓰기를 늘린다

        인덱스는 특정 값을 가진 행을 빨리 찾는 별도 구조입니다. 읽을 후보를 줄여 주지만, 데이터를 추가·변경·삭제할 때 인덱스도 함께 고쳐야 합니다. 읽기를 빠르게 하는 대가로 쓰기와 저장 공간 비용을 냅니다.

        PostgreSQL의 UPDATE는 원래 행의 바이트를 제자리에서 덮어쓰지 않습니다. MVCC 때문에 새 행 버전을 만들고, 옛 버전은 어떤 트랜잭션도 더 이상 볼 필요가 없어졌을 때 정리됩니다. 새 버전은 새 위치에 있으므로, 보통은 바꾸지 않은 열의 인덱스에도 새 위치를 가리키는 항목이 추가됩니다.보강

        이 부담을 줄이는 최적화가 HOT(Heap-Only Tuple)입니다. 다음 두 조건이 모두 맞으면 새 버전을 같은 페이지에 두고, 인덱스에 새 항목을 넣지 않습니다.S2

        1. 인덱스가 걸린 열을 바꾸지 않는다. (BRIN 같은 요약 인덱스는 예외)
        2. 옛 행이 있는 페이지에 새 버전을 넣을 빈 공간이 있다.

        UPDATE 한 행이 만드는 일

        조건을 바꿔 HOT 업데이트가 되는지, 새 인덱스 항목과 WAL 레코드가 몇 개 생기는지 보세요.

        실험 B의 테이블
        ① 바꾸는 열에 인덱스가 걸려 있나
        ② 옛 행이 있는 페이지에 빈 공간이 있나

        WAL 레코드 수는 행 하나 기준이며, 실험 B(PostgreSQL 16.13)에서 관찰한 레코드 구성으로 만든 추정입니다. 인덱스 페이지 분할, 중복 제거, full-page image 여부에 따라 달라집니다.

        “UPDATE마다 모든 인덱스가 반드시 같은 방식으로 바뀐다”고 단정하지 않는 이유가 여기 있습니다. 조건에 따라 인덱스를 건드리지 않을 수도, 모든 인덱스에 항목을 추가할 수도 있습니다. 긴 트랜잭션은 옛 버전이 필요한 기간을 늘려 정리를 늦춥니다. 그래서 쓰기 부하를 볼 때는 요청 수뿐 아니라 인덱스 수, 바뀌는 열, 행 크기, 트랜잭션 길이, VACUUM 상태를 함께 봅니다.

        Spring Boot 4 · Kotlin으로 옮기면보강 최신 상태만 메모리에 모았다가 주기적으로 한 번에 저장하는 가장 단순한 형태입니다. 프로세스가 강제로 죽으면 최대 5초 분량이 사라지므로, 이 손실을 허용할 수 있는 데이터에만 씁니다. @Scheduled를 쓰려면 @EnableScheduling이 필요합니다.

        @Component
class LatestStatusBuffer(private val repository: CaptureStatusRepository) {
    private val latest = ConcurrentHashMap<String, CaptureStatus>()

    fun accept(status: CaptureStatus) {
        // 늦게 도착한 옛 상태가 새 상태를 덮지 않도록 version으로 비교한다
        latest.merge(status.sessionId, status) { old, new -> if (new.version > old.version) new else old }
    }

    @Scheduled(fixedDelay = 5_000)
    fun flush() {
        val batch = latest.keys.mapNotNull { latest.remove(it) }
        if (batch.isEmpty()) return
        try {
            repository.upsertAll(batch)   // 직접 만든 배치 upsert 한 번으로 저장
        } catch (e: Exception) {
            batch.forEach(::accept)       // 실패하면 되돌려 넣고 다음 주기에 다시 시도
            throw e
        }
    }

    @PreDestroy
    fun flushOnShutdown() = flush()       // 정상 종료 때는 남은 값을 저장한다
}

        • 질문(접근 패턴)을 먼저 적고 그 질문에 맞는 키·인덱스를 고릅니다. 같은 인덱스가 모든 질문에 맞지는 않습니다.
        • UNIQUE·CHECK 같은 제약은 “조회한 뒤 저장”하는 사이의 틈을 저장소에서 막는 약속입니다.
        • 실행 계획은 예상 행 수와 실제 행 수의 차이부터 봅니다. 인덱스를 쓰지 않았다고 나쁜 계획은 아닙니다.
        • ORM이 SQL을 대신 만들어도 왕복 횟수와 읽는 범위의 비용은 그대로 남습니다.

        정규화는 같은 사실을 한 곳에만 둬서 고칠 곳을 분명하게 만드는 방법입니다. 조회를 빠르게 하려고 요약이나 복제본을 추가하면 새 질문이 생깁니다. 원본의 주인은 누구인가, 언제 갱신하나, 어긋난 것을 어떻게 알아내고 다시 만드나. 비정규화는 “이 복사본은 버려도 되는가”까지 함께 정하는 설계입니다.

        3.4 B-tree 인덱스와 복합 키

        B-tree 계열 인덱스는 정렬된 키를 여러 갈래로 나눠 계층적으로 좁혀 찾습니다. 모든 행을 읽는 대신 몇 개의 페이지만 거쳐 후보 범위를 찾을 수 있습니다.

        그렇다고 인덱스가 늘 이기지는 않습니다. 결과가 테이블의 대부분이라면 인덱스를 거쳐 많은 행을 하나씩 찾아가는 것보다 처음부터 훑는 순차 스캔이 나을 수 있습니다. 인덱스를 쓰지 않았다는 사실만으로 실행 계획이 나쁘다고 결론 내리지 않습니다.

        “사용자별 최신 세션 20개”를 찾는 요청이 WHERE user_id = ? ORDER BY started_at DESC LIMIT 20이라면 (user_id, started_at DESC) 인덱스가 좋은 후보입니다. 반대로 “전체 사용자의 시간 범위 조회”에는 이 인덱스가 거의 도움이 되지 않습니다. 인덱스의 첫 열이 user_id라서, 시간만으로는 정렬된 순서를 이용할 수 없기 때문입니다. 복합 인덱스의 열 순서는 실제 조건·정렬·선택도(조건이 얼마나 적은 행을 고르는가)와 DB 기능을 함께 보고 정합니다.

          4.2 원자성·격리·내구성을 나눈다
          

          트랜잭션은 관련 작업을 하나의 성공·실패 단위로 묶습니다. 그런데 트랜잭션이 주는 약속은 세 가지로 나뉘고, 셋 모두 “업무 규칙이 맞다”는 약속은 아닙니다.
          

          

          성질약속하는 것약속하지 않는 것
          


          원자성묶인 작업이 일부만 반영된 상태를 남기지 않는다동시에 도는 다른 트랜잭션과의 관계
          

          격리동시에 실행되는 작업끼리 어떤 결과를 허용할지 정한다수준에 따라 허용되는 이상 현상이 다르다
          

          내구성성공한 결과가 약속한 장애 조건에서 살아남는다약속 밖의 장애(2장)
          
          

          

          그래서 “트랜잭션을 붙였다”는 말만으로 중복 신청, 초과 예약, 외부 결제 중복이 해결되지 않습니다. 특히 같은 DB 트랜잭션에 속하지 않은 외부 API 호출은 DB를 롤백해도 취소되지 않습니다. API 호출을 트랜잭션 안으로 옮겨도 이 경계는 그대로이고, DB 연결만 더 오래 붙잡게 됩니다(9장 사례 C).
          


          4.3 읽고 나중에 쓰는 틈
          

          재고가 1개 남았습니다. A와 B가 각각 재고 1을 읽습니다. 둘 다 “남아 있으니 판매 가능”이라고 판단합니다. 각자 읽은 값에서 1을 빼 0을 쓰면, 두 요청이 모두 성공했는데 재고는 0입니다. 재고가 음수가 아니라고 초과 판매가 없었던 것은 아닙니다.
          

          아래는 같은 상황을 네 가지 방법으로 PostgreSQL 16.13에서 실제로 실행한 기록입니다. 두 연결의 실행 순서를 고정해서, “어쩌다 한 번” 일어나는 충돌을 매번 재현했습니다.보강
          


          

          재고 1개, 구매 요청 2개
          방법을 바꿔 가며 같은 순서로 실행한 결과를 비교하세요. 오래 걸린 줄은 상대 트랜잭션을 기다린 시간입니다.
          

          

          


          조건부 UPDATE가 틈을 막는 방법
          

          같은 행의 조건을 변경과 함께 검사합니다.
          

          UPDATE lab.inventory
SET stock = stock - 1
WHERE id = 1 AND stock > 0
RETURNING stock;
          

          PostgreSQL의 Read Committed에서 다른 트랜잭션이 같은 행을 먼저 바꾸는 중이면, 뒤의 UPDATE는 기다렸다가 바뀐 행을 기준으로 조건을 다시 평가합니다. A가 1을 0으로 바꿨다면 B는 stock > 0을 만족하지 못해 0행을 바꿉니다. 애플리케이션은 이 변경 행 수를 보고 품절을 처리해야 합니다. SQL과 성공 판정이 하나의 계약입니다.S4
          

          이 방법으로 모든 불변식이 풀리지는 않습니다. “여러 행의 합계가 한도를 넘지 않는다”처럼 행을 가로지르는 규칙에는 잠글 기준 행, 제약 표현, 격리 수준 같은 추가 설계가 필요합니다. 이 장의 연습 문제가 그런 경우입니다.
          

          

          Spring Data JPA에서는보강 조건부 갱신은 @Modifying 쿼리로 쓰고, 반환값(바뀐 행 수)으로 성공을 판정합니다. 같은 영속성 컨텍스트에 그 엔티티가 이미 올라와 있다면 clearAutomatically = true로 옛 값을 비웁니다. 버전 검사는 엔티티에 @Version을 두면 충돌 때 ObjectOptimisticLockingFailureException으로, 비관적 락은 @Lock(LockModeType.PESSIMISTIC_WRITE)가 SELECT … FOR UPDATE로 나갑니다.
          

          interface InventoryRepository : JpaRepository<Inventory, Long> {
    @Modifying(clearAutomatically = true)

          5.4 타임아웃·재시도·입장 제어
          

          타임아웃은 무한히 기다리는 것을 막아 줍니다. 하지만 원격 작업을 취소하거나 롤백해 주지는 않습니다. 클라이언트는 기다리기를 멈췄는데 서버의 작업은 계속될 수 있습니다. 거기에 재시도까지 더해지면 이미 느린 시스템에 일이 더 쌓입니다.
          

          세 계층이 각각 최초 시도를 포함해 3번씩 호출하고 모든 호출이 같은 이유로 실패한다면, 가장 아래 작업은 최대 27번 실행됩니다. “재시도 3번”은 “시도 4번”이라서, 이를 혼동하면 64번이 됩니다.S9
          

          

          재시도 증폭 계산기
          호출이 여러 계층을 지날 때, 계층마다 재시도하면 맨 아래 작업이 몇 번 실행되는지 계산합니다.
          

          

          



          

            

            

            

            

            재시도는 스택의 한 지점에서만 하고, 나머지 계층은 실패를 위로 올려보내는 편이 안전합니다.S9 S36 그리고 한 경로 안에서 다음을 함께 맞춥니다. 요청 전체의 마감 시간(deadline), 재시도할 오류의 종류, 최대 시도 횟수, backoff·jitter, 그리고 같은 요청을 다시 보내도 안전한가(7장 멱등성).
            

            

            Spring Framework 7에서는보강 재시도와 동시성 제한이 코어 기능으로 들어왔습니다. @EnableResilientMethods로 켜고, @Retryable과 @ConcurrencyLimit을 메서드에 붙입니다. @Retryable은 기본값으로 모든 예외에 대해 재시도하고, maxRetries는 재시도 횟수이므로 전체 시도는 1 + maxRetries번입니다. 재시도할 예외를 좁히고, 부작용이 있는 호출은 멱등 키 없이 재시도하지 않습니다.
            

            @Configuration
@EnableResilientMethods
class ResilienceConfig

@Service
class NotificationSender(private val client: PushClient) {
    @Retryable(
        includes = [ConnectException::class],  // 연결 실패만 재시도한다
        maxRetries = 2,                        // 최초 1번 + 재시도 2번 = 최대 3번 시도
        delay = 100, multiplier = 2.0, maxDelay = 1000, jitter = 50
    )
    fun send(message: Push) = client.send(message)

    @ConcurrencyLimit(20)                      // 동시에 20개까지만 진행한다
    fun sendBulk(messages: List<Push>) = client.sendAll(messages)
}

            레이트 리밋시간당 들어오는 양 (예: 초당 200건)작업이 느려지면 같은 초당 200건이어도 진행 중인 작업이 늘어난다
            

            동시성 제한동시에 진행 중인 작업 수 (예: 20개)한도를 넘는 요청을 기다리게 할지 거절할지 정해야 한다
            

            bulkhead의존성별로 자원을 나눠, 하나가 전체를 점유하지 못하게 한다나눈 칸이 너무 작으면 평소에도 거절이 생긴다

            5.5 네트워크 지연을 읽는 최소 원리
            

            TCP는 바이트를 순서대로, 빠짐없이 전달합니다. 애플리케이션의 “요청 한 건”이라는 경계를 지켜 주는 것은 아닙니다. 잃어버린 바이트를 다시 보내는 손실 복구와 네트워크 혼잡을 조절하는 혼잡 제어 때문에, 같은 양의 바이트도 왕복 지연과 손실에 따라 걸리는 시간이 달라집니다. 받는 쪽이 감당할 양을 조절하는 흐름 제어와, 네트워크 경로의 혼잡을 조절하는 혼잡 제어는 다른 것입니다.
            

            HTTP/2는 연결 하나로 여러 스트림을 처리합니다. 하지만 그 아래 TCP에서 바이트 하나를 잃으면, 그 뒤의 바이트는 다른 스트림 것이라도 순서를 지키느라 함께 기다립니다. QUIC은 스트림별로 순서를 지켜 다른 스트림으로 번지는 대기를 줄입니다. 그래도 같은 스트림 안의 순서 대기와 경로 전체의 혼잡은 없애지 못합니다.S13

            6.5 DynamoDB를 후보로 만드는 이유와 탈락 조건
            

            DynamoDB는 키 중심 접근을 제공하는 관리형 저장소입니다. 중요한 질의와 데이터의 크기·형태·변화 속도를 먼저 이해한 뒤 partition key와, 필요하면 sort key를 설계합니다. “나중에 아무 조건으로나 검색하고 조인하면 된다”보다 “중요한 접근 패턴을 미리 모델링한다”는 접근이 맞습니다.S5
            

            예시 후보는 PK = USER#사용자ID, SK = SESSION#세션ID입니다(PK, SK). 이것이 정답이라는 뜻은 아닙니다. 사용자 한 명에게 쓰기가 몰리거나, 세션 항목 하나를 매우 자주 갱신하면 문제가 남습니다. 날짜만 partition key로 잡아 오늘의 쓰기를 모두 한 곳에 모으는 설계도 위험합니다. 키 종류가 많다는 사실보다 실제 요청 분포가 중요합니다.S6
            

            숫자로 보면 분명해집니다. DynamoDB의 파티션 하나는 초당 최대 1,000 쓰기 단위를 받도록 설계됐고, 1 KB 이하 항목을 한 번 쓰면 1단위입니다.S6보강 항목 하나는 한 파티션에 있으므로, 인기 세션 항목 하나를 초당 2,000번 갱신하면 설계 한도를 넘습니다.
            


            

            키 설계 놀이터
            초당 쓰기와 쏠림 정도를 정하고 키 설계를 바꿔 보세요. 가장 뜨거운 키가 받는 쓰기와, 자주 쓰는 조회가 몇 번의 요청으로 끝나는지 함께 보입니다.
            

            

            



            

            



            

            

            

            자주 쓰는 조회이 설계에서
            

            

            사용자 1만 명, 사용자당 세션 하나, 인기 세션을 뺀 쓰기는 고르게 나뉜다고 가정한 모델입니다. 파티션 한도는 1 KB 이하 항목 기준이며, 실제 파티션 배치와 적응형 용량은 AWS가 관리합니다.
            

            

            


            애플리케이션에서 키 뒤에 접미사를 붙여 쓰기를 나누는 write sharding을 검토할 수 있습니다. 대신 읽을 때 여러 조각을 모으는 비용이 생기고, 같은 항목의 순서·원자성 요구도 다시 따져야 합니다. DynamoDB를 도입하면 키 설계나 분산에 대한 고민이 필요 없어진다는 기대는 틀립니다.
            

            후보를 평가할 때는 조건부 쓰기와 트랜잭션의 지원 범위, 읽기 일관성, 인덱스 갱신 비용, 항목 크기, 조회가 몇 곳으로 퍼지는지(fan-out), 데이터 이동과 복구를 함께 봅니다. “NoSQL은 트랜잭션이 없다” 같은 이분법은 쓰지 않습니다.S5 S17

                7장 부분 실패·중복·순서를 다루는 방법

                이 장의 핵심
                  

                • 타임아웃은 실패가 아니라 ‘결과를 모름’입니다. 이 상태를 상태 모델과 화면에 넣어야 위험한 재시도를 막을 수 있습니다.
                  • 

                • 전달과 반영은 다른 경계입니다. 같은 메시지가 다시 올 수 있으니, 한 번만 반영되게 하는 일은 받는 쪽이 맡습니다.
                  • 

                • 같은 DB라면 중복 기록과 업무 변경을 한 트랜잭션으로 커밋하고, 그다음에 ACK합니다. 두 변경의 순서만 바꿔서는 해결되지 않습니다.
                  • 

                • Outbox는 이벤트 유실을 막는 저장 경계를 만들 뿐 중복을 없애지 않습니다. 이메일·결제 같은 외부 부작용은 DB 트랜잭션 밖에 있습니다.

                7.1 먼저 알아둘 말
                

                

                이벤트와 메시지
                이벤트는 어떤 일이 일어났다는 기록입니다. 메시지는 다른 처리 주체에게 전달하는 데이터입니다.
                

                브로커·producer·consumer
                브로커는 메시지를 받아 저장하고 중계하는 시스템입니다. producer는 보내는 쪽, consumer(소비자)는 받는 쪽입니다.
                

                offset
                기록 안에서 어디까지 진행했는지 나타내는 위치 번호입니다.
                

                ACK
                정해진 단계를 확인했다는 응답입니다. 소비자의 ACK나 offset 진행은 “여기까지 처리했으니 다시 보내지 않아도 된다”는 신호입니다.
                

                멱등성
                같은 논리 작업을 여러 번 해도 결과가 한 번 한 것과 같게 만드는 성질입니다.
                

                대사
                서로 다른 기록을 비교해 누락과 불일치를 찾아 맞추는 절차입니다. 예를 들어 우리 DB의 결제 상태와 결제사의 거래 내역을 대조합니다.
                

                


                7.2 결과를 모르는 상태를 모델에 넣는다
                

                같은 프로세스 안의 함수 호출은 예외가 나도 무슨 일이 있었는지 대개 압니다. 다른 프로세스와 통신하면 사정이 달라집니다. 응답이 오지 않았을 때, 요청이 가는 길에 사라졌는지, 상대는 처리를 끝냈는데 응답만 사라졌는지, 아직 처리 중인지 보내는 쪽은 구분할 수 없습니다. 그래서 네트워크 타임아웃을 ‘확정 실패’로만 표현하면 위험한 재시도 정책이 만들어집니다.
                


                

                타임아웃 뒤에 무엇을 할까
                결제 요청이 타임아웃 났습니다. 보내는 쪽은 아래 세 경우 중 어느 것인지 모릅니다. 정책을 고르면 세 경우의 결과가 한꺼번에 보입니다.
                

                

                

                  

                  

                  

                  


                  상태 모델에는 업무에 맞게 접수 전·처리 중·성공·확정 실패·결과 확인 중 같은 상태를 둡니다. 결과 확인 중인 결제를 무조건 다시 만들지 않고, 결제사의 요청 키로 조회하거나 대사해서 확정하는 흐름이 필요할 수 있습니다. 사용자 화면과 운영 도구도 이 상태를 보여 줘야 합니다. 화면이 “결제 실패” 대신 “결제 확인 중”이라고 말해야 사용자가 서둘러 다시 결제하지 않습니다.
                  



                  7.3 전달과 반영은 다른 경계다
                  

                  at-least-once 전달은 “적어도 한 번”이므로 같은 메시지가 다시 올 가능성을 포함합니다. 소비자가 처리를 끝내고 ACK를 보내기 전에 죽으면, 브로커는 처리됐는지 모르므로 같은 메시지를 다시 보냅니다.
                  

                  exactly-once라는 말을 들으면 두 가지를 확인합니다. 입력·상태·출력 중 어느 경계에서 중복이 보이지 않는다는 뜻인가? 어떤 실패를 가정했는가? 브로커가 주는 보장이 외부 DB 변경이나 이메일·결제 API의 부작용까지 자동으로 넓어지지는 않습니다. 예를 들어 Kafka의 트랜잭션을 쓰는 exactly-once 처리는 Kafka에서 읽고 처리해 Kafka에 쓰는 경로 안의 보장입니다.보강
                  

                  멱등성은 같은 논리 작업을 반복해도 관찰할 결과가 한 번 한 것과 같도록 만드는 성질입니다. 키만 저장해 두면 충분하지 않습니다. 다음 네 가지를 정해야 합니다.

IETF httpapi 작업 그룹의 Idempotency-Key 헤더 초안은 처리 중인 키에 409(Conflict, 요청이 서버의 현재 상태와 충돌), 다른 내용으로 재사용한 키에 422(Unprocessable Content, 형식은 맞지만 처리할 수 없는 내용)로 답하라고 권합니다. 외부 결제 호출은 DB 트랜잭션 밖에서 하고, 결제사에도 같은 키를 넘깁니다.
                  

                  // CREATE TABLE idempotency_keys (
//   user_id BIGINT NOT NULL, idem_key TEXT NOT NULL,   -- 키의 범위: 사용자별
//   request_hash TEXT NOT NULL,                        -- 같은 키에 다른 내용이 왔는지 비교
//   status TEXT NOT NULL,                              -- IN_PROGRESS 또는 DONE
//   response_body TEXT,
//   expires_at TIMESTAMPTZ NOT NULL,                   -- 정리 작업이 이 시각 뒤에 지운다
//   PRIMARY KEY (user_id, idem_key));

@Service
class PaymentService(private val jdbc: JdbcClient, private val gateway: PaymentGateway) {

    fun pay(userId: Long, idemKey: String, req: PayRequest): PayResult {
        val hash = req.fingerprint()
        val claimed = jdbc.sql("""
                INSERT INTO idempotency_keys (user_id, idem_key, request_hash, status, expires_at)
                VALUES (:u, :k, :h, 'IN_PROGRESS', now() + interval '24 hours')
                ON CONFLICT (user_id, idem_key) DO NOTHING
            """)
            .param("u", userId).param("k", idemKey).param("h", hash)
            .update()                                      // 트랜잭션 밖이라 바로 커밋된다

        if (claimed == 0) {                                // 이미 본 키
            val prev = jdbc.sql("SELECT request_hash, status, response_body FROM idempotency_keys WHERE user_id = :u AND idem_key = :k")
                .param("u", userId).param("k", idemKey)
                .query { rs, _ -> Triple(rs.getString(1), rs.getString(2), rs.getString(3)) }
                .single()
            return when {
                prev.first != hash -> throw KeyReusedException()           // 422: 같은 키, 다른 내용
                prev.second == "IN_PROGRESS" -> throw InProgressException() // 409: 첫 요청이 아직 처리 중
                else -> PayResult.fromJson(prev.third!!)                  // 첫 결과를 그대로 돌려준다
            }
        }
        val result = gateway.charge(req, idempotencyKey = "$userId:$idemKey")
        // 여기서 죽으면 IN_PROGRESS로 남는다. 결제사에 같은 키로 조회해 마무리하는 복구 작업이 필요하다
        jdbc.sql("UPDATE idempotency_keys SET status = 'DONE', response_body = :b WHERE user_id = :u AND idem_key = :k")
            .param("b", result.toJson()).param("u", userId).param("k", idemKey)
            .update()
        return result
    }
}

                    7.6 병렬 처리와 offset
                    

                    Kafka의 offset은 파티션 안의 진행 위치입니다. 소비자가 커밋하는 값은 “다음에 읽을 위치”, 즉 마지막으로 처리한 메시지의 offset + 1입니다.보강 그 값을 커밋하면 앞의 메시지는 모두 끝났다는 뜻이 됩니다. 그래서 메시지를 비동기로 병렬 처리할 때, 뒤 메시지만 끝났다고 앞의 미완료 메시지까지 건너뛰어 커밋하면 안 됩니다.
                    

                    

                    어디까지 커밋해도 되나
                    한 파티션의 메시지 0~9를 병렬로 처리하는 중입니다. 칸을 눌러 완료와 처리 중을 바꿔 보세요.

                        인증은 요청자가 누구인지 확인합니다. 인가는 그 요청자가 해당 데이터와 작업에 접근해도 되는지 정합니다. 유효한 JWT를 제시했다는 이유만으로 다른 사용자의 촬영 세션을 수정할 권한이 생기지는 않습니다.
                        

                        촬영 세션 수정 API가 session_id만 받아 UPDATE한다면 소유권 검사가 빠진 것입니다. 업무에 맞게 user_id나 tenant_id와 대상 세션의 관계를 검증해야 합니다. 식별자가 추측하기 어렵다(예: UUID)는 사실을 권한 검사 대신 쓰지 않습니다. 식별자는 URL, 로그, 공유 링크로 얼마든지 새어 나갑니다.
                        

                        -- 위험: 세션 ID만으로 바꾼다. 로그인만 했으면 누구의 세션이든 바뀐다
UPDATE capture_session SET status = :status WHERE id = :sessionId;

-- 요청자와 세션의 관계를 함께 검사한다
UPDATE capture_session SET status = :status
WHERE id = :sessionId AND user_id = :currentUserId;
-- 0행이면 없는 세션과 남의 세션을 구분하지 않고 똑같이 답한다

                              8.5 API 계약은 배포 중에도 지켜야 한다
                              

                              요청·응답의 필드, 의미, 오류, 멱등 키와 재시도 가능 여부가 모두 계약입니다. 배포 중에는 옛 클라이언트와 새 서버, 새 클라이언트와 옛 서버가 함께 돕니다(10장). 필드를 추가하는 변경도 모르는 필드를 오류로 처리하는 엄격한 파서나, 새 필드를 필수 생성자 인자로 받는 코드에서는 문제가 됩니다. 그래서 실제 소비자와의 호환성 테스트가 필요합니다.

                                  장애 대응은 원인을 맞히는 시험이 아닙니다. 사용자에게 생긴 일에서 출발해 CPU·힙·p95를 각각 가설로 나누고, 증거를 남기며 되돌릴 수 있는 완화를 고릅니다. 이 책에서 가장 긴 장이라 처음에는 순서대로 읽고, 실무에서는 자기 환경에서 검증한 절차서로 바꿔 씁니다.
                                  

                                  

                                  이 장의 핵심
                                    

                                  • 출발점은 “CPU가 높다”가 아니라 “어떤 업무가 언제부터 얼마나 실패하나”입니다. 기술 지표는 그 영향을 설명하고 대응 효과를 확인하는 데 씁니다.
                                    • 

                                  • 모니터링·진단·완화·근본 수정은 끝나는 시점이 다릅니다. 재시작으로 응답이 돌아왔다면 완화에 성공한 것이지, 원인이 사라진 것은 아닙니다.
                                    • 

                                  • 같은 그래프도 원인이 다를 수 있습니다. CPU는 “무슨 일을 더 하나”, 힙은 “어떤 메모리인가”, p95는 “어디서 기다리나”로 나눠 봅니다.
                                    • 

                                  • 성공은 지표 하나로 선언하지 않습니다. CPU는 요청을 모두 거절해도 내려가고, p95는 느린 요청이 시간 초과로 빠져도 좋아 보입니다.
                                    • 

                                  

                                  이 장을 읽는 순서. 공통 대응 순서 → CPU 급증 → 힙이 줄지 않을 때 → p95 악화 → 증거 수집 → 재시작 판단 → 사례 → 실험 → 판단 연습. 예시는 JVM으로 돌아가는 Java·Kotlin 서버지만, CPU·메모리·대기를 구분하는 방법은 다른 환경에도 통합니다. 명령의 지원 범위는 실행 중인 JDK와 운영체제에서 확인합니다. 사례의 수치는 판단 연습을 위한 가정이며 보편적인 임계값이 아닙니다.

                                  메트릭은 시간에 따른 수치, 로그는 개별 사건의 기록, 트레이스는 한 요청이 지나간 경로를 연결한 기록입니다. span은 트레이스 안의 한 작업 구간입니다.
                                  

                                  label과 cardinality
                                  label은 메트릭을 구분하는 차원(예: route, status), cardinality는 서로 다른 값이나 조합의 개수입니다.
                                  

                                  가설과 관측
                                  가설은 현상을 설명하려고 검증할 주장, 관측은 실제로 측정한 자료입니다.
                                  

                                  SLI·SLO·SLA
                                  SLI는 사용자가 받은 서비스 수준을 재는 지표, SLO는 그 지표에 세운 목표, SLA는 당사자 사이의 약정입니다.
                                  

                                  


                                  9.2 먼저 사용자에게 어떤 일이 생겼는지 말한다
                                  

                                  “CPU가 높다”는 시스템의 상태입니다. “촬영 종료 요청의 8%가 실패하고 재시도 중이다”는 사용자 영향입니다. 장애 대응은 영향을 받는 기능·사용자·시간 범위를 좁히는 데서 시작합니다. 기술 지표는 그 영향을 설명하거나 대응 효과를 확인하는 데 씁니다.
                                  

                                  SLI는 측정하는 서비스 수준, SLO는 목표입니다. 예를 들어 “30일 동안 유효한 촬영 종료 요청의 99.9%를 정해진 시간 안에 성공 처리한다”는 목표를 세울 수 있습니다. 무엇을 분모에 넣고 어떤 사건을 성공으로 볼지 적어야 합니다. 접수 단계의 HTTP 200(OK, 요청을 정상 처리함)만으로 영구 저장 성공을 대신하면 뒤에서 일어나는 비동기 실패를 숨길 수 있습니다.S19
                                  

                                  

                                  오류 예산 계산기
                                  유효 요청 수와 목표를 정하면 허용되는 실패 건수가 나옵니다. 지금까지의 실패와 경과 일수를 넣으면 이 속도로 기간 끝에 예산을 얼마나 쓸지도 보입니다.
                                  

                                  

                                  



                                  

                                  



                                  

                                  

                                  

                                  

                                  

                                  유효 요청이 100만 건이고 목표 성공 비율이 99.9%라면 허용 실패는 1,000건입니다. 이것은 요청 기반 계산입니다. 모든 요청의 가치가 같다는 뜻이 아니고, “한 달에 43.2분”처럼 시간 기반 가용성의 허용 시간과 바로 바꿔 쓸 수도 없습니다.
                                  


                                  9.3 메트릭·로그·트레이스를 조합한다

                                      9.5 CPU가 치솟으면 “무슨 일을 더 하고 있나”를 찾는다
                                      

                                      90%라는 숫자의 분모부터 확인한다
                                      

                                      CPU 사용률은 일정한 관측 구간에서 CPU가 일한 비율입니다. 대시보드가 호스트 전체, 한 프로세스, 한 코어, 컨테이너에 배정한 용량 중 무엇을 분모로 쓰는지 확인합니다. 한 코어를 100%로 표현하는 도구는 여러 코어를 쓰는 프로세스를 100% 넘게 보여 줍니다. 서로 다른 기준의 90%를 그대로 비교하지 않습니다.
                                      

                                      

                                      같은 일, 다른 분모
                                      코어 수, 계속 바쁘게 도는 스레드 수, 컨테이너 CPU 한도를 바꿔 보세요. 같은 상황이 분모에 따라 얼마나 다르게 보이는지 나옵니다.
                                      

                                      

                                      상황




                                      

                                      




                                      

                                      

                                      

                                      스레드가 쉬지 않고 계산만 한다고 단순화했습니다. 실제 사용률은 스케줄링, 대기, GC 스레드에 따라 달라집니다.
                                      

                                      

                                      

                                      예를 들어 8코어 호스트에서 한 코어만 계속 바쁜 프로그램은 호스트 평균이 약 12.5%일 수 있습니다. 전체 평균은 낮아도, 요청을 처리하는 단일 스레드(프로그램 안에서 명령을 실행하는 흐름)는 이미 한계입니다. 반대로 CPU가 90%여도 작업이 지연 없이 끝나고 추가 유입을 감당한다면 그 숫자만으로 장애를 선언하지 않습니다.
                                      

                                      컨테이너는 호스트의 자원을 제한·분리해 프로세스를 실행하는 환경입니다. CPU quota는 일정 기간에 허용한 CPU 실행 시간이고, throttling은 그 예산을 다 써서 실행이 제한되는 현상입니다. 호스트가 한가로워도 컨테이너는 자기 한도를 다 쓸 수 있습니다. Linux cgroup v2의 cpu.max와 cpu.stat, 또는 플랫폼의 대응 지표를 확인합니다. 누적 제한 횟수의 총합보다 장애 구간의 증가량을 봅니다.S30
                                      

                                      CPU가 하는 일은 업무 계산만이 아니다
                                      

                                      GC(Garbage Collection)는 더 이상 도달할 수 없는 객체의 메모리를 회수하는 작업입니다. 문자열을 대량으로 만들면 업무 계산과 객체 할당, 회수 작업이 함께 늘 수 있습니다. 그래서 CPU 급증을 “반복문 버그” 하나로 좁히지 않습니다.
                                      

                                      

                                      함께 관측한 것다음 증거와 가설조치가 효과를 내는 이유·한계
                                      


                                      요청 수와 CPU가 함께 증가요청당 CPU 시간, 처리량, 새 요청 유형을 비교불필요한 요청 제한이나 비필수 작업 중지가 유입 작업량을 줄인다. DB에 여유가 있을 때 확장도 후보
                                      

                                      요청 수는 같은데 특정 경로의 CPU 증가데이터 크기와 CPU 실행 표본을 비교비싼 기능의 플래그 해제, 호환되는 롤백이 요청당 계산량을 줄인다
                                      

                                      GC 빈도·할당량도 증가GC에 쓴 CPU와 일시 정지, 객체 생성 경로큰 응답·임시 객체·과도한 동시 요청을 줄이면 메모리 작업이 준다
                                      

                                      컨테이너 제한 증가CPU 한도, 코어별 사용, 실행 대기한도 조정은 실행 예산을 늘린다. 호스트 여유와 비용을 확인해야 한다
                                      

                                      한 인스턴스만 계속 과열같은 버전의 정상 인스턴스, 특정 요청·배치·스레드와 비교해당 인스턴스 격리가 유효할 수 있다. 남은 서버의 과부하를 먼저 계산한다
                                      
                                      

                                      

                                      CPU 프로파일은 실행 중인 코드 위치를 반복해서 표본으로 모은 자료입니다. “표본의 70%가 JSON 변환 경로에 있다”는 그 경로가 계산 비용의 큰 후보라는 뜻입니다. 전체 응답 시간의 70%라고 읽지는 않습니다. 기다리는 시간은 CPU를 쓰지 않기 때문입니다. 표본 수, 기록 구간, 수집 설정에 따라서도 결과가 달라집니다.
                                      

                                      스레드 덤프는 한 시점에 스레드들이 어디서 무엇을 하는지 기록한 자료입니다. 몇 초 간격의 여러 기록에서 같은 경로가 반복되면 단서가 되지만, RUNNABLE 상태 한 장면만으로 무한 루프를 확정하지 않습니다. 이 상태에는 실행 가능하거나 일부 자원 처리를 기다리는 상황이 포함될 수 있습니다. CPU 실행 표본, 스레드별 CPU 사용, 시간 흐름과 연결해 봅니다. JDK Flight Recorder(JFR)는 실행·대기·GC 같은 사건을 기록하는 도구입니다.S31
                                      

                                      계산으로 세운 가설을 관측으로 확인한다
                                      

                                      

                                      CPU 수요 계산기
                                      초당 요청 × 요청당 CPU 시간이 초당 필요한 CPU초입니다. 코어 수와 비교해 보세요.
                                      

                                      

                                      상황




                                      

                                      




                                      

                                      

                                      

                                      

                                      

                                      

                                      가정: 2코어 인스턴스에 초당 200건이 들어오고, 요청당 평균 CPU 시간이 5ms라면 초당 CPU 수요는 200 × 0.005 = 1 CPU초입니다. 다른 작업이 없다면 2코어 용량의 약 절반입니다. 새 데이터 형식 때문에 요청당 15ms가 되면 수요가 3 CPU초로 늘어 2코어를 넘고, 대기가 쌓일 수 있습니다.
                                      

                                      여기에 응답 시간을 CPU 시간 대신 넣으면 계산이 틀립니다. 응답 시간에는 DB·네트워크·풀 대기가 들어 있습니다. 이 모형은 평균 수요만 설명하며 순간 폭주, 단일 스레드, GC, 스케줄링은 빠져 있습니다. 실제로는 요청당 계산 증가와 대기 증가를 프로파일과 트레이스로 확인합니다.
                                      

                                      조건부 완화. 새 변환 기능을 끈 뒤 요청량이 비슷한데 CPU와 대기가 내려가고 완료율이 회복되면 그 경로 가설이 강해집니다. 기능을 끄면 필요한 결과가 빠지지 않는지도 검증합니다. 한편 DB가 이미 포화인데 애플리케이션 서버만 늘리면 DB 연결과 요청을 더 늘려 상황을 악화시킬 수 있습니다.
                                      


                                      9.6 힙이 줄어들지 않으면 “어떤 메모리인가”부터 구분한다
                                      

                                      used, committed, max, RSS는 같은 숫자가 아니다
                                      

                                      

                                      힙의 used·committed·max
                                      힙(heap)은 주로 Java 객체가 놓이는 메모리 영역입니다. used는 지금 사용 중인 양, committed는 JVM이 쓸 수 있게 확보한 양, max는 그 영역이 쓸 수 있는 상한입니다. max만큼 물리 메모리가 이미 확보됐다는 뜻은 아닙니다.S32
                                      

                                      RSS
                                      프로세스의 메모리 중 지금 물리 메모리에 올라와 있는 양을 나타내는 운영체제 지표입니다. JVM 힙 외에도 스레드 스택(호출 흐름과 지역 정보를 담는 영역), 클래스 정보, 네이티브 메모리(JVM 힙 바깥에서 쓰는 메모리)가 관계합니다. 운영체제마다 산정 방식이 다르고 컨테이너 전체 메모리 지표와도 다를 수 있습니다.

RSS가 곧바로 같은 폭으로 줄어야 한다고 기대하지 않습니다. 반환 동작은 JVM, 수집기, 설정에 따라 다릅니다. (GiB는 230바이트, MiB는 220바이트입니다.)

                                      할당이 많은 것과 누수는 다르다
                                      

                                      할당(allocation)은 새 객체를 만들 메모리를 받는 일입니다. 곧 회수할 수 있는 임시 객체가 초당 많이 생겨도 오래 사는 양은 일정할 수 있습니다. 이 경우 문제는 높은 할당·회수 비용입니다. 누수(leak)는 필요가 끝난 객체를 계속 참조해 회수를 막는 경우입니다. 사용 중인 캐시나 밀린 요청도 객체를 계속 잡고 있으므로, 기준선이 오른다는 사실만으로 코드 누수를 확정할 수 없습니다.S33
                                      

                                      참조(reference)는 다른 객체로 이어지는 관계입니다. GC는 “이제 필요 없다”는 개발자의 의도를 모릅니다. 오래 보관하는 목록이 끝난 요청을 계속 참조하면 그 요청 객체는 살아 있는 것으로 취급됩니다. 힙 덤프는 이런 객체와 참조 관계를 분석하는 자료이고, 보유 경로(path to GC roots)를 보면 어떤 살아 있는 출발점이 객체를 붙잡고 있는지 찾을 수 있습니다.
                                      

                                      해석 예: byte[]가 메모리를 많이 차지한다는 클래스별 집계만으로는 원인을 알 수 없습니다. 영상 버퍼, 캐시 값, 대기 중인 요청 본문이 모두 같은 배열일 수 있습니다. 누가 보유하는지 확인해 “완료된 요청을 지우지 않은 목록”과 “아직 끝나지 않은 요청이 쌓인 큐”를 구분해야 수정 방법이 정해집니다.

                                      OutOfMemoryError와 종료 코드 137

                                      한 요청의 경로를 펼친다

                                      늘어난 구간확인할 자료완화가 작동하는 이유·주의점
                                      


                                      요청 진입·실행 대기대기 작업 수, 가장 오래 기다린 시간, 실행 스레드·CPU유입·동시성 제한으로 대기를 제한한다. 제한만으로 업무가 완료된 것은 아니다
                                      

                                      DB 연결 획득active·max·pending, 연결 보유 시간반환이 늦어지는 원인을 줄여 연결을 더 빨리 재사용한다. 풀 증설은 DB 한도를 확인해야 한다
                                      

                                      실제 SQL 실행느린 질의, 실행 계획, 락·I/O 대기잘못된 질의와 차단하는 트랜잭션을 구분한다. 취소·롤백의 비용과 업무 영향을 확인한다
                                      

                                      외부 API호출별 지연·오류·재시도, 연결 설정필수가 아닌 호출의 우회나 대기 제한으로 자원 점유를 줄인다. 데이터 의미가 바뀌는지 확인한다
                                      

                                      JVM 일시 정지GC 일시 정지 시각과 요청 지연의 겹침정지 원인이 확인되면 할당·보유량을 줄인다. 높은 힙 비율 하나로 GC 원인이라 단정하지 않는다
                                      
                                      

                                      

                                      active는 지금 사용 중인 연결 수, max는 풀의 최대 수, pending은 연결을 기다리는 요청 수입니다. 풀이 다 찼다는 것은 자원이 부족하다는 관측이지 “최댓값을 올리면 해결된다”는 결론이 아닙니다. 연결을 오래 빌리고 있거나 반환하지 않는 원인이 있다면 그것이 먼저입니다.
                                      

                                      타임아웃과 재시도는 자원 사용 정책이다
                                      

                                      타임아웃은 작업 결과를 기다릴 시간의 한도입니다. 대기를 제한하면 호출자의 스레드·연결·메모리가 오래 묶이는 것을 줄일 수 있습니다. 그러나 호출자가 기다리기를 끝내도 하위 작업이 취소되지 않으면 서버의 일은 계속됩니다. 연결, 읽기, 전체 요청의 시간 한도가 각각 무엇인지 확인하고 취소 전달과 자원 반환을 검증합니다.
                                      

                                      타임아웃을 늘리면 느린 작업이 끝날 기회를 얻는 대신 동시에 기다리는 작업이 많아질 수 있습니다. 무작정 줄이면 정상 작업도 실패하고 재시도를 부릅니다. 전체 응답 시간 예산, 하위 호출 시간, 재시도 횟수를 함께 정합니다(5장). 재시도는 이미 수행된 쓰기를 중복 실행할 수 있어 멱등성과 연결됩니다(7장). 회로 차단기는 연속으로 실패하는 하위 호출을 잠시 빠르게 거절하고 회복을 시험하는 장치일 뿐, 실패한 의존성을 고쳐 주지는 않습니다. 대체 응답의 업무 의미가 안전해야 합니다. 재시도 예산과 유입 제한은 실패한 작업이 다시 부하가 되어 실패를 늘리는 반복을 끊는 데 씁니다.S36
                                      


                                      9.8 증거 수집도 부하를 주는 작업이다
                                      

                                      가장 먼저 기존 대시보드·로그·트레이스를 시간 범위를 맞춰 보존합니다. 배포 버전, 인스턴스 식별자, 요청 수와 크기, 오류, CPU와 제한, 힙 지표의 정확한 이름, GC 정지, 풀·큐의 대기를 적습니다. 그래프를 캡처할 때는 단위와 집계 구간도 남깁니다. 재시작 뒤 “그때 무엇이 높았나”를 기억에 기대지 않기 위해서입니다.
                                      

                                      그다음 질문에 맞는 진단을 고릅니다. CPU를 어느 경로에 쓰는지 궁금하면 짧은 실행 기록, 멈춘 호출 위치가 궁금하면 스레드 기록, 객체를 붙잡는 관계가 궁금하면 힙 분석이 후보입니다. 질문 없이 모든 덤프를 연달아 모으지 않습니다.

                                      jcmd는 실행 중인 JVM에 진단 명령을 보내는 도구입니다. 아래 명령은 운영 서버용 자동 스크립트가 아니라, 이 장의 실습 프로세스에 직접 쓰는 예입니다.S37
                                      

                                      

                                      

                                      

                                      

                                      

                                      힙 덤프에는 토큰·사용자 데이터·요청 본문이 들어갈 수 있습니다. 스레드 기록과 JFR에도 경로나 질의 같은 민감한 맥락이 남을 수 있습니다. 진단 파일은 접근을 제한하고 필요한 기간만 보관합니다. 문서 형식의 문제가 아니라 실행 중인 데이터의 복사본을 만드는 일이기 때문입니다.
                                      

                                      응답이 거의 멈춘 상태에서 덤프 수집이 응답하지 않거나 피해를 늘리면 중단하고 완화를 우선합니다. 짧은 진단조차 못 남겼다는 사실을 기록하면 됩니다. 완벽한 증거가 복구의 필수 조건은 아닙니다.
                                      


                                      9.9 재시작을 조건과 검증이 있는 완화로 바꾼다

                                      재시작을 고려할 근거먼저 확인하는 이유이후 확인
                                      


                                      한 인스턴스만 멈추고 다른 인스턴스는 정상그 인스턴스의 지역 상태 문제일 수 있어 격리 효과를 기대한다남은 용량, 새 인스턴스 준비, 요청 완료율
                                      

                                      메모리 고갈이 임박하고 실패가 증가프로세스를 교체해 피해를 줄일 시간이 필요하다최소 증거, 누락·중복, 회수 후 기준선과 재발 시간
                                      

                                      알려진 문제 버전을 롤백하며 교체같은 버전을 다시 띄우는 것보다 원인을 제거할 가능성이 크다데이터·설정 호환성, 새 버전별 지표
                                      

                                      공통 DB·외부 API가 느려 전체가 악화앱을 재시작해도 공통 의존성은 빨라지지 않는다연결 폭증을 막고, 하위 병목 완화가 먼저인지 판단

                                        9.11 직접 관찰하는 작은 실험
                                        

                                        원래 교재의 실습(labs/IncidentLab.java)과 같은 구성의 프로그램을 이 교과서가 직접 작성해 실행했습니다. 외부 의존성 없이 JDK 17 이상에서 CPU 계산, 대기, 임시 할당, 객체 보유를 떼어서 관찰합니다. 서버 포트를 열거나 DB에 연결하지 않고, 보유 배열은 최대 32MiB, 실행 시간은 최대 30초로 제한했습니다. 그래도 CPU와 메모리를 실제로 쓰므로 운영 서버에서는 실행하지 않습니다.
                                        

                                        javac IncidentLab.java
java -Xms32m -Xmx128m IncidentLab selftest        # p95 예제, 입력 제한, 보유 상한 확인
java -Xms32m -Xmx128m IncidentLab cpu 3           # 한 스레드가 계산을 반복
java -Xms32m -Xmx128m IncidentLab wait 3          # 같은 시간 대부분 잠듦
java -Xms32m -Xmx128m -Xlog:gc IncidentLab transient 3   # 1MiB 배열을 만들고 바로 버림
java -Xms32m -Xmx128m -Xlog:gc IncidentLab retain 7      # 1MiB 배열을 목록에 보관(32MiB에서 멈춤)
                                        

                                        elapsed_ms는 지난 벽시계 시간, main_cpu_ms는 주 실행 스레드가 쓴 CPU 시간입니다. GC나 다른 스레드의 CPU까지 포함한 프로세스 전체 CPU가 아닙니다. retained_payload_mib는 프로그램이 명시적으로 보유한 배열 내용의 크기이며 JVM 전체 사용량이 아닙니다.
                                        

                                        

                                        모드·길이이 교과서 (Linux, OpenJDK 21)원래 교재 (macOS, JBR OpenJDK 25)해석
                                        


                                        cpu · 약 3초주 스레드 CPU 2,990ms약 2,995ms대부분의 시간을 계산에 썼다
                                        

                                        wait · 약 3초주 스레드 CPU 5ms약 19ms기다린 시간은 CPU 시간에 더해지지 않는다
                                        

                                        transient · 약 3초배열 할당 누계 397MiB, 명시적 보유 0MiB, GC 56번416MiB, 보유 0MiB많은 할당이 곧 지속 보유는 아니다
                                        

                                        retain · 약 7초배열 내용 보유 32MiB, heap used 65.5MiB32MiB, 약 66.8MiB보유한 내용 크기와 JVM 사용량은 다르다
                                        
                                        

                                        

                                        

                                        실행 중 힙: 버리는 할당과 붙잡는 할당
                                        두 실행에서 100ms마다 잰 힙 used와 committed입니다. 이 교과서가 실제로 기록한 값입니다.
                                        

                                        

                                        

                                        transient는 used가 올랐다 떨어지기를 반복하고 committed는 거의 그대로입니다. retain은 목록이 배열을 참조하므로 used가 계단처럼 오르다 멈추고, 확보한 공간(committed)도 따라 늘었습니다.
                                        

                                        표로 보기
                                        실행시각(초)used(MiB)committed(MiB)
                                        

                                        

                                        

                                        마지막 줄을 보고 “보유 32MiB를 뺀 나머지가 누수”라고 계산하면 안 됩니다. 힙에는 다른 객체도 있고 객체 헤더, 정렬, 수집기의 공간 배치가 관계합니다. 이번 GC 로그에도 G1 Humongous Allocation이 나타났습니다. humongous는 G1이 큰 객체에 쓰는 분류이며, 큰 객체는 배치 방식 때문에 내용 크기보다 많은 영역(region, G1이 힙을 나누어 관리하는 구획)을 차지할 수 있습니다.S32
                                        

                                        차이를 직접 분해해 봤습니다.보강 이 조건에서 G1의 영역 크기는 1MiB였고, 실습의 배열 하나는 1MiB 내용에 배열 헤더 16바이트가 붙어 영역 하나를 살짝 넘습니다. 큰 객체는 연속된 영역에 통째로 놓이므로 배열 하나가 영역 두 개를 차지했습니다. 배열을 16바이트만 줄여 영역 하나에 딱 맞추자 같은 32개를 보유해도 heap used가 65.1MiB에서 33.1MiB로 줄었습니다(labs/HumongousCheck.java). 영역 크기와 헤더 크기는 힙 크기와 JVM 설정에 따라 달라집니다.
                                        

                                        같은 프로세스에서 증거 수집 명령도 확인했습니다. cpu 모드를 20초 실행하는 동안 Thread.print로 남긴 기록에서 main 스레드는 RUNNABLE 상태로 IncidentLab.cpu에 있었습니다. 5초 JFR 기록에는 실행 표본(jdk.ExecutionSample)이 241개 담겼고, jfr view hot-methods에서 표본의 100%가 IncidentLab.cpu였습니다. 계산만 하는 실험이니 당연한 결과지만, 실제 서버에서는 이렇게 한 곳에 몰리지 않습니다. 실제 운영 서버의 정지 시간·부하·권한 조건은 검증한 것이 아닙니다.
                                        

                                        이 실험은 무제한 누수를 만들어 시스템을 고갈시키지 않습니다. 객체를 참조하는 코드와 메모리 현상의 관계를 보여 줄 뿐입니다. 실제 캐시의 만료, 요청 큐, 클래스 로더, 네이티브 누수는 따로 검증해야 합니다.
                                        


                                        9.12 판단 연습과 해설
                                        

                                        

                                        문제 1CPU가 95%이고 GC 정지 시간은 낮습니다. “GC가 원인이 아니다”라고 확정할 수 있을까요?
                                        

                                        해설 보기
                                        없습니다. 동시 GC는 애플리케이션과 함께 CPU를 쓸 수 있습니다. 정지 시간과 GC의 CPU 비용은 다릅니다. 실행 표본, GC 활동, 할당량, 요청당 계산을 함께 봅니다. 반대로 GC가 있다는 사실만으로 CPU 급증을 GC 탓으로 돌리지도 않습니다.
                                        

                                        

                                        

                                        문제 2힙 committed 2GiB가 하루 종일 유지되지만, used는 회수 주기 뒤 400MiB 부근으로 돌아옵니다. 재시작해야 할까요?

                                        이 정보만으로는 필요하지 않습니다. 확보한 공간이 유지되는 것과 살아 있는 객체가 계속 늘어나는 것을 구분합니다. 실제 사용자 지연, GC 비용, 전체 메모리 한도와 여유를 확인합니다. 부하가 일정하지 않거나 오래된 영역의 회수가 아직 끝나지 않았다면 기준선 해석도 보류합니다.

                                        문제 4재시작할 때마다 3시간쯤 정상이다가 힙과 지연이 다시 늘어납니다. 다음에 무엇을 조사할까요?

                                        문제 5DB 풀을 20에서 100으로 늘렸더니 애플리케이션의 pending은 줄었지만 DB 지연과 오류가 늘었습니다. 어떻게 해석할까요?

DB 전체의 동시 부하·락·I/O를 확인하고, 악화시킨 설정은 되돌리는 후보로 둡니다. 동시에 연결을 오래 쥐는 원인을 제거합니다. “우리 서버의 대기 그래프 개선”을 전체 사용자 개선으로 대신하지 않습니다.

                                        10장 바꾸고, 되돌리고, 복구할 수 있는 설계
                                        

                                        배포는 한순간이 아니라 구버전과 신버전이 함께 도는 시간입니다. 그 시간을 설계하고, 테스트를 실패 비용에 맞춰 배정하고, 백업이 아니라 복구를 검증합니다. 결정은 대안·측정·재검토 조건을 담은 짧은 ADR로 남깁니다.
                                        

                                        

                                        이 장의 핵심
                                          

                                        • 배포·마이그레이션·백필·롤백·복구는 서로 다른 일입니다. 같은 버튼처럼 다루지 않습니다.
                                          • 

                                        • 구버전과 신버전이 함께 도는 시간이 있습니다. 새 표현을 추가하고, 옮기고, 필요 없어지면 지우는 순서(expand–migrate–contract)로 나눕니다.
                                          • 

                                        • 백업 파일이 생겼다는 사실은 복구 가능성을 증명하지 못합니다. 별도 대상에 복원해 제약·불변식·앱 접근까지 확인해야 복구를 검증한 것입니다.
                                          • 

                                        • 비용에는 계속 유지할 일(백업, 모니터링, 업그레이드, 사람의 시간)이 들어갑니다.
                                          •

                                        배포

                                        마이그레이션과 백필
                                        마이그레이션은 데이터 구조나 저장 위치를 옮기는 변경, 백필은 빠진 과거 데이터를 새 구조에 채우는 일입니다.
                                        

                                        롤백과 복구
                                        롤백은 이전 상태로 되돌리는 조치, 복구는 장애 뒤 필요한 서비스·데이터 상태를 되찾는 일입니다.
                                        

                                        runbook
                                        실행 순서를 적은 운영 절차서입니다.
                                        

                                        


                                        10.2 작게 시작해도 경계는 명확히 한다
                                        

                                        같이 바뀌는 업무 규칙과 데이터를 모으고, 데이터를 최종적으로 수정할 권한을 누가 가질지 정합니다. 하나의 배포 단위 안에서도 모듈 경계와 의존 방향은 지킬 수 있습니다. 서비스 분리는 독립 배포·확장·보안·팀 운영의 이득이 분산 비용보다 클 때 검토합니다.
                                        

                                        코드가 복잡하다는 이유만으로 원격 호출로 나누면 네트워크·재시도·일관성·운영 책임이 더해집니다(7장). 반대로 분명한 독립 요구가 있는데 단일 배포만 고집할 필요도 없습니다. “언제 분리할 것인가”를 변경 빈도, 자원 요구, 장애 영향 같은 조건으로 적어 둡니다.
                                        


                                        10.3 구버전과 신버전이 함께 있는 시간
                                        

                                        컬럼 이름을 한 번에 바꾸고 서버를 차례로 배포하면, 아직 교체되지 않은 구버전이 옛 컬럼을 찾다가 실패합니다. expand–migrate–contract는 새 표현을 추가하고(expand), 호환되는 코드로 데이터를 옮기고(migrate), 더 이상 옛 표현이 필요 없을 때 지우는(contract) 단계화입니다.
                                        

                                        

                                        컬럼 하나를 안전하게 바꾸는 순서
                                        duration_sec(초)를 duration_ms(밀리초)로 바꿉니다. 단계를 넘기며 컬럼 상태, 돌고 있는 버전, 되돌릴 수 있는 범위를 보세요. SQL 결과는 이 교과서가 PostgreSQL 16.13에서 실행한 기록입니다.
                                        

                                        

                                        

                                          

                                          

                                          

                                          

                                          

                                          두 곳에 쓰는 기간에는 부분 실패와 “어느 쪽이 원본인가”라는 문제가 생깁니다. 백필은 다시 실행해도 안전해야 하고, 처리 위치·오류·대사 결과를 기록해야 합니다. dual write라는 이름을 붙였다고 원자성이 생기지는 않습니다. 삭제나 되돌릴 수 없는 변환 뒤에는 코드 롤백만으로 돌아갈 수 없을 수 있습니다.
                                          

                                          

                                          Spring Boot 4 + Flyway로 나누면보강 Boot 4에서는 Flyway 자동 구성이 별도 스타터로 나뉘어 spring-boot-starter-flyway를 추가해야 하고, PostgreSQL을 쓰면 Flyway의 PostgreSQL 모듈도 필요합니다. expand와 contract는 서로 다른 배포에 넣습니다. 큰 표의 백필은 서버가 시작할 때 도는 마이그레이션에 넣지 말고, 구간별로 다시 실행할 수 있는 별도 작업으로 돌립니다.
                                          

                                          dependencies {
    implementation("org.springframework.boot:spring-boot-starter-flyway")
    implementation("org.flywaydb:flyway-database-postgresql")
}
                                          

                                          -- V7__add_duration_ms.sql        (배포 1: expand)
ALTER TABLE capture_session ADD COLUMN duration_ms bigint;

-- V9__drop_duration_sec.sql      (배포 4 이후: contract, 옛 접근이 모두 사라진 뒤)
ALTER TABLE capture_session DROP COLUMN duration_sec;
                                          

                                          

                                          기능 플래그와 카나리 배포는 노출 범위를 줄이는 수단입니다. 카나리에 들어가는 트래픽이 실제로 중요한 사용 패턴을 포함하는지 확인하고, 오류·지연·업무 지표의 중단 기준을 미리 정합니다. 배포 성공과 업무 정상은 별개입니다.
                                          


                                          10.4 테스트를 실패 비용에 배정한다
                                          

                                          

                                          대상알맞은 테스트이유
                                          


                                          순수 계산, 상태 전이빠른 단위 테스트경우의 수를 싸게 많이 확인할 수 있다
                                          

                                          SQL, 제약, 트랜잭션, 직렬화실제 구현에 가까운 통합 테스트경계의 의미가 중요하다. 흉내 낸 DB는 UNIQUE나 격리 수준을 재현하지 못한다
                                          

                                          외부 계약호환성 검증필드 추가도 소비자를 깨뜨릴 수 있다(8장)
                                          

                                          핵심 사용자 흐름소수의 전체 경로 테스트느리고 깨지기 쉬우니 꼭 필요한 흐름만
                                          

                                          동시성, 중복, 부분 성공, 배포 중 공존실패 시점을 고정한 작은 테스트정상 요청 하나로는 검증되지 않는다(4장·7장 실험)
                                          
                                          

                                          

                                          실패 시점을 고정한 작은 테스트가 “모두 정상 동작함”이라는 큰 테스트보다 원인을 더 잘 보여 줄 수 있습니다. 테스트가 구현을 그대로 따라 쓰면 같은 실수를 재현한 채 통과할 수 있다는 점도 기억합니다.
                                          


                                          10.5 백업 성공과 복구 성공은 다르다
                                          

                                          

                                          RPO
                                          Recovery Point Objective. 복구할 때 허용하는 데이터 손실의 시간 범위 목표입니다. “최대 5분치까지 잃어도 된다.”
                                          

                                          RTO
                                          Recovery Time Objective. 서비스를 복구하기까지 걸리는 시간의 목표입니다. “1시간 안에 다시 쓸 수 있어야 한다.”
                                          

                                          

                                          복제본은 삭제나 오염도 함께 반영하므로 백업과 같은 역할이 아닙니다. 백업 파일이 생성됐다는 사실만으로 복구 가능성이 증명되지도 않습니다.
                                          

                                          

                                          RPO·RTO 계산기
                                          대비 방식과 장애 종류를 고르면, 최악의 경우 잃는 데이터와 복구에 걸리는 시간이 나옵니다. 속도와 소요 시간은 가정값입니다.

                                          복구 실험은 별도 대상에 백업을 복원하고 행 수뿐 아니라 핵심 제약, 업무 불변식, 애플리케이션 접근까지 확인합니다. 걸리는 시간에는 파일 복원 말고도 권한, DNS, 설정, 클라이언트 전환, 검증이 들어갈 수 있습니다. 다시 재생할 로그와 복구 지점을 얼마나 보존하는지도 점검합니다.S22

                                          두 번 복원했습니다. 처음에는 백업 파일만, 두 번째는 계정(전역 객체)을 먼저 옮긴 뒤입니다.
                                          

                                          

                                          

                                            

                                            

                                            

                                            

                                            데이터와 제약은 완벽히 돌아왔는데 앱은 접속조차 못 했습니다. pg_dump는 데이터베이스 하나를 백업하므로 계정 같은 클러스터 전역 객체는 들어 있지 않습니다. 행 수만 세고 “복구 성공”이라고 했다면 놓쳤을 문제입니다. 이 실험은 전체 서비스 장애 복구나 PITR, 관리형 DB의 RPO·RTO를 증명하지 않습니다. 작은 검증에서 출발해 범위를 넓히는 첫걸음입니다.
                                            


                                            10.6 비용에는 계속 유지할 일이 포함된다
                                            

                                            RDB·DynamoDB·Redis의 비용을 비교할 때 월 사용료만 넣지 않습니다. 데이터 보존, 백업·복구, 인덱스·복제, 모니터링, 데이터 이동, 업그레이드, 담당자가 이해하고 장애에 대응하는 시간을 넣습니다. 사람의 시간은 불확실하므로 범위와 가정을 함께 적습니다.
                                            

                                            기술을 하나 더하면 장애 때 따져야 할 조합도 늘어납니다. 반복되는 실제 문제를 줄이는지, 운영 소유자가 있는지, 제거·교체 조건이 무엇인지 묻습니다. 이미 쓴 비용은 앞으로 계속 쓸 근거가 아니지만, 전환 비용 역시 무시할 수 없습니다.
                                            


                                            10.7 짧은 ADR의 완성 예시
                                            

                                            ADR(Architecture Decision Record)은 결정과 그 이유를 짧게 남기는 기록입니다. 아래는 이 책의 사례로 쓴 한 페이지 예시입니다.
                                            

                                            

                                            ADR-012 · 촬영 상태 쓰기 부하에 대한 임시 결정
                                            

                                            

                                            문제
                                            학습용 서비스의 최신 촬영 상태가 RDB 쓰기 부하의 큰 비중을 차지한다. 실제 측정은 아직 없으며 대안 검증이 필요하다.
                                            

                                            제약
                                            확정 이벤트는 손실 불가. 최신 상태는 5초 지연 허용. 작은 운영팀. 실제 키 분포와 피크 부하는 아직 모름.
                                            

                                            후보
                                            기존 RDB의 쓰기·인덱스 개선, 상태 갱신 합치기, DynamoDB로 상태 분리, RDB 샤딩. Redis는 상태 보관·합치기의 실패 조건이 맞을 때 별도 후보.
                                            

                                            임시 결정
                                            먼저 RDB에서 상태와 이벤트의 논리 경계를 나누고 비용 원인을 측정한다. 중간 상태 생략이 허용되는 경로만 합치기 실험을 한다. 현재 근거만으로 저장소 이전은 확정하지 않는다.
                                            

                                            검증
                                            같은 고유 업무 요청과 내구성 조건에서 DB 지연·WAL·IOPS·오류·누락과 운영 비용을 비교한다. 이득이 작거나 허용 지연을 넘으면 합치기를 중단한다.
                                            

                                            재검토
                                            현재 저장 경로의 한계가 측정되고, 키 중심 접근과 분산 가능한 부하가 확인되며, 이전·복구 계획이 준비되면 DynamoDB PoC(아이디어의 가능성을 작게 검증하는 작업)를 진행한다.
                                            

                                            

                                            이 문서는 특정 제품의 정답을 선언하지 않고, 다음 결정을 가능하게 합니다.
                                            

                                            

                                            

                                            내 ADR 쓰기
                                            칸을 채우면 오른쪽 점검표가 초록색으로 바뀝니다. 이 브라우저에 저장되고, 마크다운으로 복사할 수 있습니다.
