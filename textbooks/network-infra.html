    도메인: 인터넷 주소의 "이름"

    IP 주소는 외우기 어려우니 사람이 읽는 이름을 붙인 것. 그 이름을 누가, 어떻게 관리할까요?

    도메인 해부하기 (조각을 눌러보세요)

    조각을 선택하세요.

    도메인을 둘러싼 세 주체

    주체역할이번 경우
    레지스트리 (Registry)TLD 전체를 관리하는 기관. 장부의 원본을 가짐.ua 레지스트리
    레지스트라 (Registrar)레지스트리에 대신 등록해주는 판매 대리점nic.ua
    등록자 (Registrant)도메인 주인나

    nic.ua에서 한 일은 레지스트리 장부에 "이 도메인의 네임서버는 Cloudflare야"라고 적은 것뿐이에요. 도메인 소유권은 여전히 nic.ua를 통해 관리돼요.

    서브도메인은 공짜

    내가 산 건 ssobbs13.pp.ua 하나예요. 그 아래 api., www., admin.은 DNS 레코드 한 줄로 무한히, 무료로 만들 수 있어요. 서브도메인에는 "서버"가 필요 없어요. 그냥 이름표예요.

    Public Suffix List (PSL)

    pp.ua, co.kr, github.io, pages.dev처럼 "이 아래 이름은 각자 다른 주인"이라고 정한 공개 목록이에요. 브라우저는 이 목록으로 쿠키를 격리하고, Cloudflare는 ssobbs13.pp.ua를 독립 도메인으로 인정해요.

    도메인의 일생: 만료되면 바로 사라질까?

    아니에요. 만료일이 지나도 며칠~수십 일 동안 되찾을 기회가 있어요. 대신 뒤로 갈수록 비싸지고, 마지막엔 아무도 못 막아요.

    만료 타임라인 (gTLD 기준, 단계를 눌러보세요)

    .com 같은 gTLD 기준이에요. .ua 같은 국가 도메인(ccTLD)은 기간과 규칙이 레지스트리마다 달라요. 정확한 건 nic.ua 약관을 확인하세요.

    WHOIS와 RDAP: 도메인 등기부 등본

    whois ssobbs13.pp.ua          # 레지스트라, 만료일, 네임서버, 상태 코드
curl -s https://rdap.org/domain/example.com | jq   # WHOIS의 후속 표준 (JSON)

    clientHold / serverHoldDNS에서 빠짐. 만료, 미납, 신원 확인 미완료 때 걸려요. 사이트가 통째로 사라져요

    Q. admin.ssobbs13.pp.ua를 쓰고 싶다. 무엇을 해야 할까?
    서브도메인은 DNS 레코드 한 줄이에요. 구매도, 서버도 필요 없어요. 터널을 쓰면 route 추가 시 레코드가 자동 생성돼요.
    Q. 만료일을 3일 넘겨서 사이트가 안 뜬다. 가장 알맞은 설명은?
    만료 직후는 보통 유예 기간(Grace)이에요. 레지스트라가 DNS를 멈추거나 주차 페이지로 바꾸지만, 갱신하면 그대로 돌아와요.

    DNS: 이름을 주소로 바꾸는 전화번호부

    브라우저가 가장 먼저 하는 일은 "이 이름의 IP가 뭐지?"를 묻는 것.

    DNS 조회 시뮬레이터

    두 종류의 DNS 서버

    • 권한 있는 네임서버 (Authoritative): 정답 원본을 가진 서버. 지금은 cash / virginia.ns.cloudflare.com
    • 리졸버 (Recursive Resolver): 대신 물어보고 캐시하는 서버. 통신사 DNS, 8.8.8.8, 1.1.1.1

    레코드 타입 탐색기

    TTL과 "전파"의 정체

    TTL(Time To Live)은 리졸버가 답을 캐시하는 시간(초)이에요. "DNS 전파에 24시간 걸린다"는 말의 정체는 전 세계 리졸버의 캐시가 만료되기를 기다리는 시간이에요. 뭔가 퍼져나가는 게 아니에요.

    캐시는 한 군데가 아니에요
    
  
    "레코드를 바꿨는데 나만 옛날 IP가 나와요"의 원인은 대부분 아래 캐시 중 하나예요. 위에서부터 차례로 확인해요.
    
  
    
    
    순서캐시 위치비우는 법
    
    
    1브라우저 DNS 캐시 (Chrome은 약 1분)chrome://net-internals/#dns → Clear host cache
    
    
    2OS 캐시 + /etc/hosts (hosts 파일이 DNS보다 우선)macOS sudo dscacheutil -flushcache, Windows ipconfig /flushdns
    
    
    3공유기 DNS 프록시재부팅하거나 리졸버를 1.1.1.1로 직접 지정
    
    
    4리졸버 (통신사, 8.8.8.8, 1.1.1.1)못 비워요. TTL 만료를 기다리거나 dig @1.1.1.1로 다른 리졸버에 물어봐요. Cloudflare는 1.1.1.1 캐시 삭제 페이지를 제공해요
    
  
    
  
    없다는 답도 캐시돼요 (negative caching)레코드를 만들기 전에 한 번 조회했다면, 리졸버는 "없음(NXDOMAIN)"이라는 답도 SOA 레코드에 적힌 시간만큼 캐시해요. 그래서 레코드를 먼저 만들고 나서 조회하는 습관이 좋아요.
    
  
    DoH / DoT원래 DNS 질문은 평문 UDP 53번이라 통신사가 보고 바꿀 수도 있어요. DNS over HTTPS(443)와 DNS over TLS(853)는 이걸 암호화해요. 브라우저의 "보안 DNS" 설정이 DoH예요. 켜두면 OS나 공유기 캐시를 건너뛰기도 해서, 디버깅할 때 결과가 다르게 나올 수 있어요.
    

  
    apex와 CNAME@(= ssobbs13.pp.ua 자체)는 원래 규칙상 CNAME을 못 가져요. Cloudflare는 CNAME Flattening으로 몰래 A 레코드처럼 바꿔줘서 가능하게 해줘요.
    

  
    
    
    Q. api 레코드를 xxx.cfargotunnel.com으로 연결하려면 어떤 타입을 써야 할까?
    
    
    
      
      
      
      
    
    
    
    이름 → 다른 이름(별칭)은 CNAME. A는 이름 → IP 주소예요.
    
  
    
  
    
    
    Q. 주황 구름인 api CNAME 레코드를 dig +short api.ssobbs13.pp.ua로 조회하면?

    NAT: 사설 IP가 인터넷에 나가는 방법

    "포트 열었는데 안 돼요"의 90%는 OS 방화벽을 안 열어서예요. 터널을 쓰는 지금은 둘 다 닫아두는 게 정답. SSH(22)만 열어두세요.
    

  
    상태 기반(stateful) 방화벽OCI Security List의 기본 규칙은 stateful이에요. 안에서 나간 연결의 응답은 인바운드 규칙이 없어도 자동으로 들어와요. 그래서 cloudflared는 인바운드 규칙 하나 없이 엣지와 대화할 수 있어요.

    SSL/TLS 모드 선택기
    
    
    
    
    
    
    
  
    

  
    터널을 쓰면②구간이 터널 자체로 암호화돼요. http://localhost:8080처럼 평문으로 적어도 안전해요. 평문 구간은 서버 내부뿐이에요. nginx도, certbot도, 인증서 파일도 필요 없어요.
    

  
    터널 없이 직접 오픈한다면: Origin CA 인증서
    
  
    Full (strict)를 쓰려면 오리진에도 믿을 만한 인증서가 있어야 해요. Let's Encrypt 대신 Cloudflare가 무료로 주는 Origin CA 인증서(최대 15년)를 쓸 수 있어요. 단, 이 인증서는 Cloudflare 엣지만 믿어요. 브라우저가 오리진에 직접 접속하면(회색 구름) 경고가 떠요.
    

  
    HSTS: "이 사이트는 앞으로 무조건 HTTPS"
    
  
    Strict-Transport-Security: max-age=31536000; includeSubDomains
    
  
    이 헤더를 한 번 받은 브라우저는 max-age 동안 http://로 접속하려 해도 스스로 https://로 바꿔요. 처음 한 번의 평문 요청을 가로채는 공격(SSL stripping)을 막아요. Cloudflare의 SSL/TLS → Edge Certificates에서 켤 수 있어요.
    
  
    HSTS는 되돌리기 어려워요includeSubDomains를 켜면 모든 서브도메인이 HTTPS를 강제당해요. HTTPS가 안 되는 서브도메인이 하나라도 있으면 그곳은 max-age 동안 접속 불가예요. max-age=300처럼 짧게 시작해서 늘리세요. preload는 브라우저에 하드코딩되는 거라 빼는 데 몇 달 걸려요.

    용어뜻
    
    
    포워드 프록시클라이언트 쪽 대리인 (회사 프록시, VPN)
    
    
    리버스 프록시서버 쪽 대리인. 요청을 대신 받아 뒤로 넘김 (nginx, Caddy, Cloudflare)
    
    
    CDN전 세계에 서버를 두고 가까운 곳에서 응답하는 네트워크
    
    
    엣지CDN의 각 서버. 커넥터가 붙어있던 icn(인천)이 그 예
    
    
    오리진진짜 원본 서버. OCI의 Spring 앱
    
    
    Anycast여러 서버가 같은 IP를 쓰고, 가장 가까운 곳으로 자동 연결

    캐시
    
  
    정적 파일(JS, CSS, 이미지)은 엣지 캐시로 빨라져요(Pages가 자동으로 해줘요). API 응답은 기본적으로 캐시 안 돼요. 캐시 규칙을 잘못 만들면 남의 일기가 보이는 사고가 날 수 있어요. Spring에서 Cache-Control 헤더로 제어하세요.
    

  
    
    
    엣지 캐시 시뮬레이터: 같은 요청을 두 번 보내면?
    
    
    
      
      
    
    
    
    
      
      
    
    
    
    
  
    

  
    
    
    CF-Cache-Status뜻
    
    
    HIT엣지 캐시에서 바로 응답. 오리진은 몰라요
    
    
    MISS캐시에 없어서 오리진에 갔다 옴. 다음 요청부터 HIT
    
    
    EXPIRED / REVALIDATED캐시가 만료돼서 오리진에 다시 받음 / 오리진이 304로 "그대로 써"라고 함
    
    
    BYPASS캐시 대상이지만 오리진 헤더(private, no-store, Set-Cookie) 때문에 건너뜀
    
    
    DYNAMIC애초에 캐시 대상이 아님 (HTML, API 기본값). 가장 흔한 값
    
  
    
  
    브라우저 개발자 도구 → Network → 응답 헤더에서 바로 볼 수 있어요. curl -sI https://…/app.js | grep -i cf-cache로도 확인해요.
    

  
    리버스 프록시가 덧붙이는 헤더
    
  
    프록시를 거치면 오리진이 보는 "접속자"는 프록시 자신이에요. 그래서 프록시는 원래 정보를 헤더에 적어서 넘겨줘요.
    
  
    
    
    헤더담긴 정보Spring에서
    
    
    X-Forwarded-For원래 클라이언트 IP (프록시를 지날 때마다 뒤에 추가)request.remoteAddr (설정 후)
    
    
    X-Forwarded-Proto원래 스킴 (https)request.isSecure, 리다이렉트 URL
    
    
    X-Forwarded-Host원래 Host절대 URL 생성
    
    
    CF-Connecting-IPCloudflare가 확인한 사용자 IP 하나직접 꺼내 쓰기 가장 쉬움
    
  
    
  
    헤더는 위조할 수 있어요누구나 X-Forwarded-For: 1.2.3.4를 붙여 보낼 수 있어요. 믿어도 되는 건 내가 신뢰하는 프록시가 붙인 값뿐이에요. 터널 구조에선 오리진에 들어오는 모든 요청이 Cloudflare를 거치니 안전하지만, 포트를 직접 열었다면 Cloudflare IP 대역에서 온 요청만 믿어야 해요.

    Chapter 7
    
  
    브라우저 보안 모델: CORS와 쿠키
    
  
    FE와 API 도메인이 달라지는 순간 반드시 만나는 것.
    

  
    Origin과 Site
    
  
      
    
    • Origin = 스킴 + 호스트 + 포트. 하나라도 다르면 다른 origin
      • 
    
    • Site = 등록 가능한 도메인(PSL 기준). api.ssobbs13.pp.ua와 ssobbs13.pp.ua는 같은 site
      • 
  
    

  
    
    
    Origin / Site 판별기
    
    
    
      
      
    
    
    
    
    
    
  
    

  
    CORS
    
  
    브라우저는 기본적으로 다른 origin의 응답을 JS가 못 읽게 막아요. CORS는 서버가 "이 origin은 읽어도 돼"라고 허락하는 헤더예요.
    
  
    Access-Control-Allow-Origin: https://ssobbs13.pp.ua
Access-Control-Allow-Credentials: true
    
  
    PUT/DELETE, JSON 본문, Authorization 헤더를 쓰면 브라우저가 먼저 OPTIONS 요청(preflight)을 보내요. Spring Security가 OPTIONS를 막으면 CORS 에러가 나요.
    
  
    CORS는 서버 보안이 아니다브라우저만 지키는 규칙이에요. curl이나 Postman은 무시해요. 인증과 권한은 Spring Security가 따로 해야 해요.
    

  
    
    
    Preflight 시뮬레이터: 이 fetch는 OPTIONS를 먼저 보낼까?
    
    
    
      
      
    
    
    
    
      
      
      
    
    
    
    
    
    
  
    

  
    Spring Security에서 CORS 켜기 (Kotlin)
    

    @Bean
fun corsConfigurationSource(): CorsConfigurationSource {
    val config = CorsConfiguration().apply {
        allowedOrigins = listOf("https://ssobbs13.pp.ua", "http://localhost:5173")
        allowedMethods = listOf("GET", "POST", "PUT", "PATCH", "DELETE")
        allowedHeaders = listOf("Authorization", "Content-Type")
        allowCredentials = true      // 쿠키를 쓴다면
        maxAge = 3600                // preflight 결과를 1시간 캐시
    }
    return UrlBasedCorsConfigurationSource().apply { registerCorsConfiguration("/**", config) }
}

@Bean
fun filterChain(http: HttpSecurity): SecurityFilterChain = http
    .cors { }                         // 위 Bean을 사용. 인증 필터보다 먼저 OPTIONS를 처리해요
    .build()
    
  
    자주 하는 실수① allowCredentials = true인데 allowedOrigins = listOf("*") → Spring이 시작할 때 막아요. 와일드카드가 필요하면 allowedOriginPatterns. ② origin 끝에 /를 붙임(https://ssobbs13.pp.ua/) → 불일치. ③ @CrossOrigin만 붙이고 Security에 .cors { }를 안 켬 → preflight가 401로 막혀요.
    

  
    쿠키 속성
    
  
    
    
    속성뜻
    
    
    Domain=ssobbs13.pp.ua서브도메인끼리 공유
    
    
    SameSite=Lax같은 site 요청 + 링크 이동 시 전송 (기본값)
    
    
    SameSite=None; Secure다른 site에도 전송 (서드파티)
    
    
    HttpOnlyJS에서 못 읽음 (XSS 방어)
    
    
    SecureHTTPS에서만 전송
    
  
    
  
    그래서FE를 pages.dev가 아니라 ssobbs13.pp.ua 커스텀 도메인에 두면, API와 같은 site가 되어 쿠키 인증이 훨씬 쉬워져요.
    

  
    CSRF: 쿠키가 자동으로 따라가서 생기는 문제
    
  
    쿠키는 요청을 누가 시켰든 브라우저가 알아서 붙여요. 악성 사이트가 <form action="https://api.ssobbs13.pp.ua/diaries/7" method="POST">를 몰래 제출하면, 로그인된 사용자의 쿠키가 함께 가요. 이게 CSRF예요. CORS는 응답을 읽는 것만 막고 요청 전송은 막지 않아서 CSRF를 못 막아요.
    
  
    
    
    인증 방식CSRF 위험대책
    
    
    쿠키 세션 / 쿠키에 JWT있음SameSite=Lax(cross-site POST에 쿠키 안 보냄) + Spring Security CSRF 토큰
    
    
    Authorization: Bearer 헤더없음브라우저가 자동으로 붙이지 않아서 안전. 대신 토큰 보관 위치가 XSS에 노출돼요 (암호학 챕터 참고)
    
  
    
  
    주의: api.ssobbs13.pp.ua와 evil.ssobbs13.pp.ua는 same-site예요. SameSite는 같은 site 안의 다른 서브도메인은 막지 못해요. 서브도메인을 남에게 내주지 마세요.
    

  
    
    
    Q. https://ssobbs13.pp.ua 페이지에서 https://api.ssobbs13.pp.ua를 fetch하면?
    
    
    
      
      
      
    
    
    
    호스트가 달라서 cross-origin이지만, 등록 도메인이 같아서 same-site예요.
    
  
    
  
    
    
    Q. fetch(url, {method:"POST", headers:{"Content-Type":"application/json"}, body}). 콘솔에 CORS 에러가 났는데 Network 탭엔 OPTIONS 401이 보인다. 원인은?
    
    
    
      
      
      
    
    
    
    preflight에는 쿠키도 Authorization도 안 붙어요. 인증 필터보다 CORS 처리가 먼저 돼야 해요. Security 설정에 .cors { }를 켜세요.

      •

    로드밸런싱 알고리즘
    
  
    
    
    알고리즘방식잘 맞는 경우
    
    
    라운드 로빈차례대로 하나씩요청 처리 시간이 비슷할 때 (기본값)
    
    
    가중 라운드 로빈성능 좋은 서버에 더 많이서버 사양이 다를 때
    
    
    최소 연결지금 연결이 가장 적은 서버로요청마다 처리 시간이 크게 다를 때 (파일 업로드, 긴 쿼리)
    
    
    IP 해시 / 스티키 세션같은 사용자는 같은 서버로세션을 메모리에 둔 레거시. 새로 만든다면 stateless로 가세요
    
  
    

  
    헬스체크 두 종류와 우아한 종료
    
  
      
    
    • Liveness (/actuator/health/liveness): "프로세스가 살아있나?" 실패하면 재시작
      • 
    
    • Readiness (/actuator/health/readiness): "지금 요청 받을 준비됐나?" 실패하면 트래픽에서 잠시 뺌 (기동 중, DB 연결 끊김)
      • 
    
    • Graceful shutdown: 배포할 때 처리 중인 요청을 끝내고 종료. Spring Boot 3.4부터 server.shutdown=graceful이 기본값이에요. 레플리카를 하나씩 교체하면 무중단 배포가 돼요.
      • 
  
    

  
    가용성은 곱셈이에요

    가용성 계산기

    지금까지 배운 것 대부분이 L7(HTTP)이었어요. 이 챕터는 그 전체를 한 장의 지도로 정리해요.
    

  
    왜 계층으로 나누나각 계층은 바로 아래 계층만 믿고 자기 일만 해요. HTTP는 TCP가 데이터를 순서대로 전달해준다고 믿고, TCP는 IP가 목적지까지 패킷을 옮겨준다고 믿어요. 그래서 Spring 개발자는 광케이블을 몰라도 API를 만들 수 있어요.

    "왜 엣지가 가까우면 빠를까?"를 숫자로 이해하는 챕터.
    

  
    TCP vs UDP
    
  
    
    
    TCPUDP
    
    
    연결3-way handshake로 연결 후 전송연결 없이 바로 전송
    
    
    보장순서 보장, 유실 시 재전송보장 없음 (앱이 알아서)
    
    
    속도느림 (확인 절차)빠름
    
    
    용도HTTP/1.1, HTTP/2, DB, SSHDNS, 영상통화, 게임, QUIC(HTTP/3)
    
  
    

  
    
    
    TCP 3-way handshake
    
    
    
    
    
  
    

  
    RTT: 지연시간의 기본 단위
    
  
    RTT(Round Trip Time)는 패킷이 갔다 오는 시간이에요. 서울↔서울 엣지는 수 ms, 서울↔미국은 150ms 이상이에요. 빛의 속도는 못 이기니까, 왕복 횟수를 줄이거나 거리를 줄이는 것이 성능 최적화의 핵심이에요.
    

  
    
    
    첫 요청 지연시간 계산기
    
    
    
      
      
    
    
    
    
    
    CDN이 빠른 이유TCP/TLS 핸드셰이크 왕복은 가까운 엣지(RTT 수 ms)와 해요. 엣지 ↔ 오리진 구간은 이미 열린 연결을 재사용해서, 먼 거리를 왕복하는 횟수가 1번으로 줄어요.
    
  
    

  
    HTTP 버전
    
  
    
    
    버전전송특징
    
    
    HTTP/1.1TCP연결당 요청 하나씩 (keep-alive로 재사용). 앞 요청이 막히면 뒤도 대기 (HOL blocking)
    
    
    HTTP/2TCP한 연결에 여러 요청 동시 전송(멀티플렉싱), 헤더 압축. 하지만 TCP 패킷 하나가 유실되면 전부 대기
    
    
    HTTP/3QUIC (UDP)TCP의 HOL 문제 해결, 핸드셰이크와 TLS를 합쳐 더 빠름. 모바일 네트워크 전환에도 강함
    
  
    
  
    
    
    HOL blocking 체험: 패킷을 눌러 유실시켜 보세요
    
    
    
    
    요청 세 개(A: 일기 목록, B: 프로필, C: 이미지)가 한 연결에서 패킷 3개씩 번갈아 도착해요.
    
    
    
    
    
  
    

  
    우리 구조에서브라우저 ↔ Cloudflare는 HTTP/2나 HTTP/3(자동), cloudflared ↔ Cloudflare는 QUIC(UDP 7844)이에요. 서버 방화벽이 아웃바운드 UDP를 막으면 cloudflared는 HTTP/2(TCP 7844)로 자동 전환해요. cloudflared → Spring은 평범한 HTTP/1.1이에요.
    

  
    연결 재사용과 타임아웃 (백엔드 입장)
    
  
    핸드셰이크가 비싸니까 연결은 재사용하는 게 기본이에요. Spring이 다른 API나 DB를 부를 때도 같아요. DB는 HikariCP가 연결을 풀(pool)로 들고 있고, HTTP 클라이언트도 커넥션 풀을 써요.
    
  
    
    
    타임아웃무엇을 기다리나안 걸면 생기는 일
    
    
    connect timeoutTCP(+TLS) 연결이 맺어지기까지상대 서버가 방화벽에 막혀 조용하면 OS 기본값(수십 초~2분)만큼 멈춤
    
    
    read (socket) timeout연결 후 응답 바이트가 오기까지상대가 느리면 스레드가 무한정 묶임 → 스레드 풀 고갈 → 내 서버도 죽음
    
    
    pool acquire timeout풀에서 빈 연결을 받기까지 (Hikari connectionTimeout, 기본 30초)느린 쿼리가 연결을 다 잡고 있으면 모든 요청이 줄 서서 대기
    
  
    
  
    타임아웃은 바깥이 안쪽보다 길어야 해요브라우저 → Cloudflare(100초) → Spring → 외부 API. Spring의 외부 API read timeout이 120초면, Cloudflare는 이미 524를 줬는데 Spring은 계속 일하고 있어요. 안쪽으로 갈수록 짧게 두세요.
    

  
    
    
    Q. HTTP/2에서 요청 A의 패킷 하나가 유실됐다. 요청 B와 C는?
    
    
    
    
    HTTP/2는 요청을 나눠 보내지만, 그 아래 TCP는 하나의 바이트 줄이에요. 앞 바이트가 없으면 뒤 바이트를 앱에 못 넘겨요. QUIC은 스트림별로 순서를 관리해서 B, C는 계속 진행돼요.
    
  
    
  
    
    
    Q. HTTP/3가 사용하는 전송 계층 프로토콜은?
    
    
    
    
    HTTP/3는 UDP 위의 QUIC을 써요. 재전송과 순서 보장은 QUIC이 스트림 단위로 직접 해요.

    Docker 네트워크: 컨테이너 안의 localhost
