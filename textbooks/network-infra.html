    Chapter 1

    도메인: 인터넷 주소의 "이름"

    IP 주소는 외우기 어려우니 사람이 읽는 이름을 붙인 것. 그 이름을 누가, 어떻게 관리할까요?

    도메인 해부하기 (조각을 눌러보세요)

    조각을 선택하세요.

    도메인을 둘러싼 세 주체

    주체역할이번 경우
    레지스트리 (Registry)TLD 전체를 관리하는 기관. 장부의 원본을 가짐.ua 레지스트리
    레지스트라 (Registrar)레지스트리에 대신 등록해주는 판매 대리점nic.ua
    등록자 (Registrant)도메인 주인나

    nic.ua에서 한 일은 레지스트리 장부에 "이 도메인의 네임서버는 Cloudflare야"라고 적은 것뿐이에요. 도메인 소유권은 여전히 nic.ua를 통해 관리돼요.

    서브도메인은 공짜

    내가 산 건 ssobbs13.pp.ua 하나예요. 그 아래 api., www., admin.은 DNS 레코드 한 줄로 무한히, 무료로 만들 수 있어요. 서브도메인에는 "서버"가 필요 없어요. 그냥 이름표예요.

    Public Suffix List (PSL)

    pp.ua, co.kr, github.io, pages.dev처럼 "이 아래 이름은 각자 다른 주인"이라고 정한 공개 목록이에요. 브라우저는 이 목록으로 쿠키를 격리하고, Cloudflare는 ssobbs13.pp.ua를 독립 도메인으로 인정해요.

    꼭 기억할 것만료일 2027-09-25, 자동 갱신 꺼짐. 만료되면 사이트가 통째로 죽고 남이 가져갈 수 있어요. Auth code(EPP)는 도메인 이전용 비밀번호라 절대 공유하면 안 돼요.
    Q. admin.ssobbs13.pp.ua를 쓰고 싶다. 무엇을 해야 할까?
    서브도메인은 DNS 레코드 한 줄이에요. 구매도, 서버도 필요 없어요. 터널을 쓰면 route 추가 시 레코드가 자동 생성돼요.
    Chapter 2

    DNS: 이름을 주소로 바꾸는 전화번호부

    브라우저가 가장 먼저 하는 일은 "이 이름의 IP가 뭐지?"를 묻는 것.

    DNS 조회 시뮬레이터

    두 종류의 DNS 서버

    • 권한 있는 네임서버 (Authoritative): 정답 원본을 가진 서버. 지금은 cash / virginia.ns.cloudflare.com
    • 리졸버 (Recursive Resolver): 대신 물어보고 캐시하는 서버. 통신사 DNS, 8.8.8.8, 1.1.1.1

    레코드 타입 탐색기

    TTL과 "전파"의 정체

    TTL(Time To Live)은 리졸버가 답을 캐시하는 시간(초)이에요. "DNS 전파에 24시간 걸린다"는 말의 정체는 전 세계 리졸버의 캐시가 만료되기를 기다리는 시간이에요. 뭔가 퍼져나가는 게 아니에요.

    TTL 계산기: 레코드를 바꾸면 언제 모두에게 반영될까?

    apex와 CNAME@(= ssobbs13.pp.ua 자체)는 원래 규칙상 CNAME을 못 가져요. Cloudflare는 CNAME Flattening으로 몰래 A 레코드처럼 바꿔줘서 가능하게 해줘요.
    Q. api 레코드를 xxx.cfargotunnel.com으로 연결하려면 어떤 타입을 써야 할까?
    이름 → 다른 이름(별칭)은 CNAME. A는 이름 → IP 주소예요.

    Rules리다이렉트, 헤더 변경

    용어뜻

    주황 구름 vs 회색 구름

    구름을 눌러 바꿔보세요

    캐시

    정적 파일(JS, CSS, 이미지)은 엣지 캐시로 빨라져요(Pages가 자동으로 해줘요). API 응답은 기본적으로 캐시 안 돼요. 캐시 규칙을 잘못 만들면 남의 일기가 보이는 사고가 날 수 있어요. Spring에서 Cache-Control 헤더로 제어하세요.

    Chapter 7

    브라우저 보안 모델: CORS와 쿠키

    FE와 API 도메인이 달라지는 순간 반드시 만나는 것.

    Origin과 Site

    • Origin = 스킴 + 호스트 + 포트. 하나라도 다르면 다른 origin
    • Site = 등록 가능한 도메인(PSL 기준). api.ssobbs13.pp.ua와 ssobbs13.pp.ua는 같은 site

    Origin / Site 판별기

    CORS

    브라우저는 기본적으로 다른 origin의 응답을 JS가 못 읽게 막아요. CORS는 서버가 "이 origin은 읽어도 돼"라고 허락하는 헤더예요.

    Access-Control-Allow-Origin: https://ssobbs13.pp.ua
Access-Control-Allow-Credentials: true

    PUT/DELETE, JSON 본문, Authorization 헤더를 쓰면 브라우저가 먼저 OPTIONS 요청(preflight)을 보내요. Spring Security가 OPTIONS를 막으면 CORS 에러가 나요.

    CORS는 서버 보안이 아니다브라우저만 지키는 규칙이에요. curl이나 Postman은 무시해요. 인증과 권한은 Spring Security가 따로 해야 해요.

    쿠키 속성

    속성뜻
    Domain=ssobbs13.pp.ua서브도메인끼리 공유
    SameSite=Lax같은 site 요청 + 링크 이동 시 전송 (기본값)
    SameSite=None; Secure다른 site에도 전송 (서드파티)
    HttpOnlyJS에서 못 읽음 (XSS 방어)
    SecureHTTPS에서만 전송
    그래서FE를 pages.dev가 아니라 ssobbs13.pp.ua 커스텀 도메인에 두면, API와 같은 site가 되어 쿠키 인증이 훨씬 쉬워져요.
    Q. https://ssobbs13.pp.ua 페이지에서 https://api.ssobbs13.pp.ua를 fetch하면?
    호스트가 달라서 cross-origin이지만, 등록 도메인이 같아서 same-site예요.

    부하 분산과 가용성

    커넥터 2개가 이미 레플리카 구조예요.

    레플리카 시뮬레이터: 요청을 보내고 레플리카를 죽여보세요

    레플리카를 눌러 죽이거나 살릴 수 있어요.
    • 헬스체크: /actuator/health를 주기적으로 찔러 죽은 레플리카를 빼요

    보안 계층: 누가 무엇을 막나

    여러 겹의 방어. 한 겹이 뚫려도 다음 겹이 막아요.

    공격을 골라 어디서 막히는지 보세요

    인증 vs 인가

    • 인증 (Authentication): 너 누구야? → 로그인, JWT
    • 인가 (Authorization): 너 이거 해도 돼? → RBAC (ROLE_USER, ROLE_ADMIN)
    • 객체 단위 권한: 이 일기가 네 거야? ← 가장 많이 놓치는 곳
    IDOR 주의GET /diaries/123에서 123만 바꾸면 남의 일기가 보이는 취약점. 역할(RBAC)만으로는 못 막아요. 매 요청마다 "이 리소스 주인 == 현재 사용자"를 확인하세요.

    Cloudflare Access는?

    엣지에서 동작하는 문지기예요(터널과 별개 제품). BE에 Spring Security로 인증과 권한이 제대로 있으면 필수가 아니라 추가 방어층이에요. 이번 프로젝트는 제거 예정이에요.

    Q. 로그인한 사용자 A가 /diaries/999(B의 일기)를 조회할 수 있었다. 무엇이 빠졌나?
    A는 인증됐고 ROLE_USER도 있어요. 빠진 건 "이 일기의 주인이 A인가" 체크예요.

    OSI 계층 모델: 네트워크의 지도

    지금까지 배운 것 대부분이 L7(HTTP)이었어요. 이 챕터는 그 전체를 한 장의 지도로 정리해요.

    왜 계층으로 나누나각 계층은 바로 아래 계층만 믿고 자기 일만 해요. HTTP는 TCP가 데이터를 순서대로 전달해준다고 믿고, TCP는 IP가 목적지까지 패킷을 옮겨준다고 믿어요. 그래서 Spring 개발자는 광케이블을 몰라도 API를 만들 수 있어요.

    계층을 눌러 살펴보세요

    실무에서는 L5/L6를 따로 나누지 않고 TCP/IP 4계층(응용 · 전송 · 인터넷 · 네트워크 접근)으로 보는 경우가 많아요. 대화에서 가장 자주 나오는 건 L3(IP) · L4(포트/TCP) · L7(HTTP) 세 개예요.

    Q. 로그인 API를 초당 수천 번 정상 HTTP 요청으로 두드리는 공격. OCI 방화벽(L4)으로 막을 수 있을까?
    L4는 포트와 IP만 봐요. 요청 내용과 빈도를 봐야 하는 L7 공격은 WAF나 Rate Limiting이 막아요.

    TCP, UDP, HTTP 버전, 그리고 지연시간

    "왜 엣지가 가까우면 빠를까?"를 숫자로 이해하는 챕터.

    TCP vs UDP

    TCPUDP
    연결3-way handshake로 연결 후 전송연결 없이 바로 전송
    보장순서 보장, 유실 시 재전송보장 없음 (앱이 알아서)
    속도느림 (확인 절차)빠름
    용도HTTP/1.1, HTTP/2, DB, SSHDNS, 영상통화, 게임, QUIC(HTTP/3)

    TCP 3-way handshake

    RTT: 지연시간의 기본 단위

    RTT(Round Trip Time)는 패킷이 갔다 오는 시간이에요. 서울↔서울 엣지는 수 ms, 서울↔미국은 150ms 이상이에요. 빛의 속도는 못 이기니까, 왕복 횟수를 줄이거나 거리를 줄이는 것이 성능 최적화의 핵심이에요.

    첫 요청 지연시간 계산기

    CDN이 빠른 이유TCP/TLS 핸드셰이크 왕복은 가까운 엣지(RTT 수 ms)와 해요. 엣지 ↔ 오리진 구간은 이미 열린 연결을 재사용해서, 먼 거리를 왕복하는 횟수가 1번으로 줄어요.

    HTTP 버전

    버전전송특징
    HTTP/1.1TCP연결당 요청 하나씩 (keep-alive로 재사용). 앞 요청이 막히면 뒤도 대기 (HOL blocking)
    HTTP/2TCP한 연결에 여러 요청 동시 전송(멀티플렉싱), 헤더 압축. 하지만 TCP 패킷 하나가 유실되면 전부 대기
    HTTP/3QUIC (UDP)TCP의 HOL 문제 해결, 핸드셰이크와 TLS를 합쳐 더 빠름. 모바일 네트워크 전환에도 강함
    우리 구조에서브라우저 ↔ Cloudflare는 HTTP/2나 HTTP/3(자동), cloudflared ↔ Cloudflare는 QUIC(UDP 7844)이에요. 서버 방화벽이 아웃바운드 UDP를 막으면 cloudflared는 HTTP/2(TCP 7844)로 자동 전환해요. cloudflared → Spring은 평범한 HTTP/1.1이에요.
    Q. HTTP/3가 사용하는 전송 계층 프로토콜은?
    HTTP/3는 UDP 위의 QUIC을 써요. 재전송과 순서 보장은 QUIC이 스트림 단위로 직접 해요.

    HTTP 의미론: 메서드, 상태 코드, 헤더

    L7의 언어. API 설계와 캐시, 재시도, 에러 처리가 전부 여기서 나와요.

    메서드 속성 탐색기

    • 안전(Safe): 서버 상태를 안 바꿈 → 크롤러, 프리페치가 마음대로 호출해도 됨
    • 멱등(Idempotent): 여러 번 해도 결과가 같음 → 네트워크 오류 시 자동 재시도해도 안전
    • 캐시 가능: 엣지나 브라우저가 응답을 저장해도 됨
    POST 중복 문제POST는 멱등이 아니라서, 타임아웃 후 재시도하면 일기가 두 번 저장될 수 있어요. 결제처럼 중요한 곳에서는 Idempotency-Key 헤더로 중복을 막아요.

    상태 코드 사전

    401 vs 403 (Spring Security에서 자주 헷갈림)401 = "너 누군지 모르겠어" (로그인 필요). 403 = "누군지 아는데 넌 안 돼" (권한 부족). 남의 일기 조회(IDOR)는 403이나, 존재 자체를 숨기려면 404를 주기도 해요.

    꼭 알아야 할 헤더

    헤더방향역할
    Host요청어느 도메인에 대한 요청인지. 터널 ingress 매칭의 기준
    Authorization요청Bearer <JWT> 형태의 인증 정보
    Cookie / Set-Cookie요청 / 응답세션 쿠키 주고받기
    Content-Type양쪽본문 형식 (application/json)
    Cache-Control응답캐시 가능 여부와 기간. API는 no-store나 private
    Origin요청CORS 판단 기준. 브라우저가 자동으로 붙임
    CF-Connecting-IP / X-Forwarded-For요청프록시 뒤에서 진짜 사용자 IP
    CF-Ray응답Cloudflare 요청 추적 ID. 문제 신고와 로그 검색에 사용

    HTTP는 무상태(stateless)

    HTTP 요청은 서로를 기억하지 못해요. 로그인 상태를 유지하려면 매 요청마다 쿠키(세션 ID)나 토큰(JWT)을 들고 와야 해요. 이게 8장의 레플리카와 세션 문제, 7장의 쿠키 이야기로 이어져요.

    Q. 네트워크가 끊겨 응답을 못 받았다. 자동 재시도해도 안전한 요청은?
    PUT은 멱등이라 여러 번 해도 결과가 같아요. POST는 일기가 중복 생성될 수 있어요.

    암호학 기초: TLS와 JWT를 이해하기 위한 최소한

    수학은 몰라도 돼요. 도구 네 가지가 각각 무엇을 보장하는지만 알면 돼요.

    도구보장하는 것비유우리 프로젝트에서
    해시무결성 (바뀌었는지 확인), 되돌릴 수 없음지문비밀번호 저장 (BCrypt)
    대칭키 암호기밀성. 같은 키로 잠그고 품집 열쇠TLS의 실제 데이터 암호화 (AES)
    비대칭키 암호공개키로 잠그면 개인키로만 풀림우체통 (누구나 넣고, 주인만 꺼냄)TLS 키 교환
    전자서명진위 (누가 썼는지), 위변조 방지도장인증서, JWT 서명

    해시 체험 (SHA-256)

    한 글자만 바꿔도 결과가 완전히 달라져요(눈사태 효과). 결과로 원문을 되돌릴 수 없어요.

    비밀번호는 SHA-256으로 저장하면 안 돼요SHA-256은 너무 빨라서 무차별 대입에 약해요. Spring Security의 BCryptPasswordEncoder처럼 일부러 느리고 솔트(salt)를 섞는 전용 해시를 쓰세요. 같은 비밀번호라도 사용자마다 다른 결과가 나와요.

    TLS 핸드셰이크 (단순화)

    TLS 1.3 핸드셰이크 따라가기

    비대칭키는 느려서 키 교환에만 쓰고, 실제 데이터는 빠른 대칭키로 암호화해요. 인증서의 서명이 "이 공개키는 진짜 api.ssobbs13.pp.ua의 것"임을 보증해요.

    JWT: 서명된 출입증

    JWT는 헤더.페이로드.서명 세 부분을 점으로 이은 문자열이에요. 앞의 두 부분은 암호화가 아니라 Base64 인코딩이라 누구나 읽을 수 있어요. 서명은 "서버가 발급했고 내용이 안 바뀌었다"를 보장할 뿐이에요.

    JWT 해부기 (브라우저 안에서만 디코딩, 외부 전송 없음)

    JWT 규칙① 페이로드에 비밀번호·개인정보를 넣지 마세요(누구나 읽음). ② 서명 키는 서버에만. ③ exp(만료)를 짧게. ④ 실제 JWT를 온라인 디코더 사이트에 붙여넣지 마세요.
    Q. JWT 페이로드에 "role":"USER"가 있다. 사용자가 이걸 "ADMIN"으로 바꿔서 보내면?
    내용은 누구나 바꿀 수 있지만, 서명 키가 없으니 올바른 서명을 만들 수 없어요. 서버가 서명을 검증하면 거부돼요. 그래서 서명 검증은 절대 생략하면 안 돼요.
